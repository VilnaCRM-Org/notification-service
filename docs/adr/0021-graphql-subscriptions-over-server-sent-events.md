# 0021. GraphQL subscriptions over Server-Sent Events

Planning decisions: the protocol choices P1 to P20 of the PRD in `specs/8-graphql-subscriptions-over-sse/prd.md`, specified by its FR-1 to FR-21 and bounded by NFR-3, NFR-5, NFR-7 and NFR-8; the reason of each choice is the assumption written under its requirement, and the design is the section "Decision Record" of `specs/8-graphql-subscriptions-over-sse/architecture.md`. Amends [ADR 0007](0007-api-contracts.md).

## Context

Frontends query the service through GraphQL at `/api/graphql` (`eventTypes`, `eventStreamStatus`), but they could not receive its events through GraphQL. The schema had no subscription root, as [ADR 0007](0007-api-contracts.md) records ("with no subscription"), so a GraphQL client had to open a second connection to `GET /api/events/stream` or `GET /api/events/ws`, with its own frame format, errors and reconnect handling. Issue #8 asks for the event stream as a GraphQL subscription served over Server-Sent Events, sent to the GraphQL endpoint with `Accept: text/event-stream`, and excludes a GraphQL WebSocket protocol.

The design has to keep what the event stream already guarantees. Every node reads the topic itself and shares no state with another node ([ADR 0013](0013-every-node-reads-kafka-directly.md), [ADR 0014](0014-no-election-lock-or-link-between-nodes.md)). Delivery is at least once, and the client deduplicates by the envelope id ([ADR 0017](0017-at-least-once-with-client-side-deduplication.md)). The request budget `HTTP_REQUEST_TIMEOUT` bounds only the time to a response head, and a node that cannot take a subscriber answers the 503 problem. Two properties of the libraries shape the transport: async-graphql runs a subscription lazily, so a refusal or an invalid argument shows only once the operation is driven, and axum's Server-Sent Events type cannot write a `data:` line without a value. The clients to serve are the graphql-sse client, urql, Apollo through a link, and the browser `EventSource`, which can only send GET and cannot set a header.

## Decision

The GraphQL subscription is one more subscriber of the node's hub. It has the window, the replay from Kafka, the cursor and type rules, the subscriber cap, the readiness rule, the shutdown and the slow-client handling of the SSE and WebSocket routes, and adds no configuration variable, no bounded context and no state shared between requests. The `events` field and its `Event` object live in the event-stream application crate; the transport, the negotiation and the root rule live in the composition root. Each point below names the protocol choices of the PRD that it records, with their reasons.

**1. Protocol (P1 to P3).** The service speaks graphql-sse in its distinct connections mode only (P1): every request carries one operation and its own stream. The single connection mode is not served, because its reservation lives in the memory of one node across a PUT, the stream, every POST and a DELETE, which needs sticky sessions or shared state, and ADR 0013 and ADR 0014 exclude both; the protocol's own recipes say the distinct mode suffices for most uses, and HTTP/2 at the edge lifts the browser limit of 6 connections per origin that the single mode works around. Its PUT reservation gets the 405 problem. There is no GraphQL WebSocket protocol (`graphql-ws`, `graphql-transport-ws`): the issue excludes it, and the plain WebSocket route stays as it is. The endpoint is `/api/graphql` itself and not a sibling path (P2), because the issue sends the subscription and the query to the GraphQL endpoint, and the graphql-sse client, urql and GraphQL Yoga use one URL for both transports. The transport is chosen by `Accept`, read as a list of media ranges with q values (P3), because the reference handler's exact comparison with `text/event-stream` would break urql's subscriptions (`text/event-stream, multipart/mixed`), a "contains" test would stream urql's queries, which list `text/event-stream` with the same q as the JSON types, and GraphQL over HTTP (section 4.2) asks the server to use the highest-priority type it supports. On POST the event stream is chosen only when `text/event-stream` outranks both JSON types; ties and wildcards stay on JSON, today's default, so no existing POST client changes transport. On GET the event stream is the only representation besides the development explorer, so a wildcard range admits it (RFC 9110, section 12.5.1); a GET without `Accept` keeps today's answer, which GraphQL over HTTP permits and which leaves every caller of today unchanged, and `text/html` or a JSON type ranked as high keeps today's answer too, so a browser navigation still gets the explorer in `dev` and the 405 problem elsewhere.

**2. Request formats (P4, P18).** The POST form takes the JSON body of GraphQL over HTTP (section 4.4), the request every server must support and the one the graphql-sse client always sends. The GET form takes `query`, `operationName`, `variables` and `extensions` in the query string (section 4.3) and exists for `EventSource`, which can only send GET and cannot set headers; it is served in every `APP_ENV`, because pages that use `EventSource` run in production (P4). The query string is bounded by `HTTP_MAX_BODY_BYTES` and answered with the 414 problem beyond it, so that a document has the same byte budget in both forms without a new variable; GraphQL over HTTP (section 5.4) names 414 for this case (P18). `variables` and `extensions` that are not JSON objects get the 422 problem with one violation, the query-parameter convention of the codebase. JSON queries over GET are not added, because POST serves queries: a GET that does not negotiate the event stream keeps its 405 problem with `Allow: POST`, a deliberate deviation from RFC 9110 (section 15.5.6) that keeps today's answer. Amended by [ADR 0022](0022-every-route-in-the-openapi-document.md), point 6 (maintainer decision M5 of 2026-11-21): on both forms `query` holds at most 4 096 and `operationName` at most 128 Unicode code points (P18), and a longer member gets the 422 length problem of point 5.

**3. Schema and resume (P5, P8).** The subscription root `Subscription` has one field, `events(types: [String!]!, lastEventId: String): Event!`, and the object is `Event { id: String!, type: String!, data: JSON! }`, the object of a WebSocket frame (P5), so one shape on every transport lets a client share its parser. `Event.id` is a decimal string, because event ids are 64-bit and exceed GraphQL `Int` and the integers a JavaScript number holds exactly. `Event.data` is one `JSON` scalar holding the whole envelope object, because the producer's `data` member is any JSON value and one scalar keeps the value identical to the SSE and WebSocket forms. The query root is unchanged and no mutation root is added, because events enter only through the topic. The cursor of a subscription is the `Last-Event-ID` header when present, else the `lastEventId` argument (P8): the header wins, as on the REST streaming routes, because an `EventSource` reconnects with its original URL, whose document may still hold an old argument, plus a newer header, and the graphql-sse client re-sends its first body on a retry while the application adds the header through the client's `headers` function on every attempt. Every carrier that is present must hold a cursor, so a malformed `lastEventId` is refused also beside a valid header. The window and the replay of the event stream serve the resume unchanged.

**4. Wire (P6, P7, P13, P16, P19).** The stream carries `next` per execution result, `complete` with a bare `data:` line after a single result, the comment `:` as keep-alive, and nothing else (P6): `next` and `complete` are the only events of graphql-sse, and its client treats any other event name as fatal. `complete` carries a bare `data:` line because the protocol requires it: an `EventSource` does not dispatch an event whose data buffer is empty, a `data:` line adds a line feed to that buffer, and urql does not read a `data:` line without a value as a result, as it would read `data: null`. Every subscription result carries `id: <event id>`, a single result none, and no `retry:` field is written (P7): an `EventSource` stores the id and sends it back as `Last-Event-ID`, the graphql-sse and urql parsers ignore it, and a query or an error result never changes a client's last event id; the graphql-sse client ignores `retry:` and backs off at random on its own, and a fixed server delay would bring the `EventSource` clients of a node back together without the random part of the documented reconnect procedure. The keep-alive comment follows the head at once and then every `STREAM_KEEP_ALIVE` without a write (P13): some browsers show a fetched response only after its first body bytes, and every stream of the service follows this one setting, which is also the socket send bound. The head is `text/event-stream` without a charset, `cache-control: no-cache`, `x-accel-buffering: no` and `vary: accept`, with no `connection` header (P19): it mirrors the SSE route so that proxies treat both streams alike, the format is always UTF-8, and a `connection` header is forbidden in HTTP/2. A query over SSE gets one `next`, then `complete`, as the issue asks and the reference handler does; a mutation is a document error, because the schema has no mutation root (P16). The bytes are written by hand, because `axum::response::sse` writes no `data:` line for an empty value.

**5. Errors and limits (P9, P10, P11, P18).** Before the stream the service answers only transport errors (on POST the 415, 413, 400 and 422 problems of today, in today's order; on GET the 414, 400 and 422 problems), the 503 states and the 503 problem of the request budget (P9). Document errors, a breach of the root rule and invalid arguments of `events` are answered inside the accepted stream: one `next` carrying the errors, then `complete` (P10). The protocol requires validation that runs before execution to report through an accepted connection, because a 4xx makes an `EventSource` fail without telling the page why and makes the graphql-sse client retry a request that cannot succeed. The root rule and invalid arguments carry `VALIDATION_FAILED` with the codes and messages of the REST routes, so a client meets one rule; document errors keep async-graphql's messages and gain no code, so the GraphQL error model stays one model. The root rule is enforced by the service as the direct-field rule (exactly one field selection written directly at the root, no root fragment, no `@skip` or `@include` there), because async-graphql has no single-root-field rule, `subscription { a: events(..) b: events(..) }` would otherwise register two hub subscribers and interleave two id sequences on one stream, and async-graphql makes one stream per direct field of the root and skips root fragments, so the wording of the GraphQL specification would let a root fragment run nothing and two selections of `events` with one response name register two subscribers. Availability is the 503 problem of the REST streaming routes before the stream, for a node that is starting, at its subscriber capacity or shutting down (P11): availability is not a validation step, GraphQL over HTTP names 503 for load shedding, and the graphql-sse client retries any answer other than 2xx after a random delay, possibly on another node, while an error result followed by `complete` would end its subscription for good. The limits are the body and the query string within `HTTP_MAX_BODY_BYTES`, depth 16, complexity 1 000, one root field, 100 type names of at most 128 characters, a 64-bit cursor, one operation per request and `MAX_SUBSCRIBERS` for all transports together (P18). `Event.data` costs 501, more than half of the complexity limit, so one execution result holds one copy of the event object: aliases and fragments are allowed, async-graphql builds one copy of a JSON value per selection, and a document that selected `data` hundreds of times under aliases would otherwise build that many copies of every event of its type per subscriber in the node's memory. The cost refuses every document that selects `data` twice, keeps `{ id type data }` valid and needs neither a new variable nor a new rule. Amended by [ADR 0022](0022-every-route-in-the-openapi-document.md), point 6 (maintainer decision M5 of 2026-11-21): the limits of P18 also hold `query` to at most 4 096 and `operationName` to at most 128 Unicode code points, on both forms, and the last transport error, on both forms and both transports, is the 422 problem of type `/problems/validation-failed` with one `length` violation per member over its bound, which never echoes the value: on POST after the 415, 413, 400 and 422 problems of today, on GET after the 414, 400 and 422 problems. A JSON client whose document or operation name exceeds its bound therefore gets this problem instead of a result, the one change of today's JSON transport that the maintainer approved.

**6. The head after the decision (P12).** The transport drives the operation, inside `HTTP_REQUEST_TIMEOUT`, until the `events` field registered its hub subscriber, the hub refused it, or the operation produced its first result; only then does it write the head or the 503 problem (P12). async-graphql runs a subscription lazily, so driving it to one of these points is the only way to answer a refusal with a 503 and to keep a query inside the request budget, and "pending at the first poll" is no usable signal, because a subscription yields on idle steps. A per-request link (`StreamLink`) in the request data carries the `Last-Event-ID` header to the field, the phase back to the transport and the event id of each result: the transport reads the decision from the phase, never from which future completed first, and learns each id from the link and not from the client's selection set, which may omit or alias `id`. The subscription takes its first step only after the head is decided, so registering reads no broker and the replay runs inside the stream. When the budget expires first, the request answers the 503 problem of the budget, and dropping the operation drops its subscriber, so no slot stays taken.

**7. Ends and slow clients (P14, P15).** `complete` is written only after a single result (P15). A subscription stream that is cut, because its client left, the node shuts down, a replay below the window cannot read Kafka (logged as `replay failed` with the transport `graphql-sse`) or the tail loop died, ends without it, so that clients resume: the graphql-sse client retries a connection that closed while results were expected and never reconnects after `complete`, and an `EventSource` reconnects with `Last-Event-ID` unless the page closed it, which the page does when it sees `complete`. A GraphQL subscriber is a hub subscriber for slow clients too (P14): publishing never waits for it, a full queue makes it fall behind and catch up on its own connection, its resolution and encoding run in its connection's task, and the send bound of every accepted connection ends a connection that accepts no data. One rule for every transport keeps the publish path unchanged, and a slow GraphQL client affects only itself.

**8. Caching and CORS (P17, P20).** Every event stream and every answer to a GET or HEAD of `/api/graphql` carries `Vary: accept` (P20), because the representation of that URL now depends on `Accept` (RFC 9110, section 12.5.5) and a shared cache could otherwise hand a stored 405 problem or explorer page to an `EventSource` request. The router's `vary_accept` layer sets it outside the panic catcher and the request budget, so their 500 and 503 answers carry it too, and inside the CORS layer, which appends its own `Vary` values. POST answers stay as they are, because caches do not reuse them without explicit freshness, which the service never sends. The CORS allow-list of `CORS_ALLOWED_ORIGINS` is unchanged (P17): it already allows `GET`, `POST`, `content-type` and `last-event-id`, the `Accept` values of the reference clients are CORS-safelisted, and no credentials are offered because there is no subscriber authorization.

**9. Amendment of ADR 0007.** This record amends the sentence of [ADR 0007](0007-api-contracts.md) (`docs/adr/0007-api-contracts.md:15`) that the GraphQL root types are `Query` and `Mutation` "with no subscription": the schema has the subscription root `Subscription` with the one field `events`, no mutation root, and `/api/graphql` answers GET and POST with an event stream when `Accept` negotiates it. ADR 0007 is a template record and is not rewritten; the [decision record index](README.md) marks it "(amended by 0021)".

## Consequences

A GraphQL client receives the events on the connection it already uses, with the same `Event` object as a WebSocket client, and needs no second connection. The nodes stay stateless: each request is self-contained, any node serves any request, a 503 is safe to retry on any node, and a client resumes on any node with its last id. A GraphQL subscriber counts in `subscribers` and against `MAX_SUBSCRIBERS` together with the SSE and WebSocket subscribers, and holds what an SSE subscriber holds plus the one execution result it is writing. A healthy subscription writes no log entry, and the fixed messages of the event stream stay the only ones: `replay failed` gains the transport value `graphql-sse`.

The guarantees of the other streams apply unchanged: delivery is at least once, and the client deduplicates by `Event.data.id`, the envelope id, never by `Event.id`, which is the position of the event. There is no subscriber authorization for the GraphQL subscription either, so the topic must carry only events that are safe for every client. async-graphql's document errors may quote the client's own request back to that client, as on the JSON transport, while no log entry, problem or error built by the service holds a value of the request.

An operation error arrives inside a 200 stream, so a client reads it from the result and not from the status; only the transport problems and the 503 answers come before a head. The direct-field rule refuses more documents than the wording of the GraphQL specification (a root fragment, `@skip` or `@include` at the root), and never runs more or fewer than one subscriber. The 405 problem of a GET without an event-stream `Accept` keeps `Allow: POST`, while the `Allow` of the other methods lists `GET, HEAD, POST`, and in `dev` curl's default `*/*` negotiates the event stream instead of the explorer: a GET with a `query` parameter streams, and one without it gets the 400 problem "Failed to deserialize query string: missing field `query`". A HEAD that negotiates the event stream registers and frees a subscriber within the request.

Browsers on HTTP/1.1 open at most 6 connections per origin, and the single connection mode that would work around it is not served, so the edge proxy should speak HTTP/2 with clients; it must not buffer `text/event-stream` on `/api/graphql` and needs an idle time-out above `STREAM_KEEP_ALIVE` (`docs/operations.md`, section "The edge proxy"). The transport changes template files of the composition root (the GraphQL module, its handler and schema, the router); `.templatesyncignore` lists them, and the new files of the transport do not exist in the template, so a template sync does not overwrite it.

Alternatives rejected: the single connection mode (a reservation in the memory of one node); a GraphQL WebSocket protocol (excluded by the issue); a sibling path for the stream (clients use one URL); an exact or "contains" match of `Accept` (breaks urql); validation errors as 4xx answers before the stream (an `EventSource` cannot read them, and the graphql-sse client retries them); a refusal as an error result inside the stream (it would end a graphql-sse subscription for good); the GraphQL specification's wording of the single root field (a root fragment would run nothing); a typed envelope object for `Event.data` (possible later without breaking the field); axum's Server-Sent Events type (no bare `data:` line); a `retry:` field (it would synchronise reconnects); and `complete` at the end of a cut subscription (clients would not resume).
