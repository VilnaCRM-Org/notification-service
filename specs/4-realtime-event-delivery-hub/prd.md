# PRD: Real-time event delivery hub (issue #4)

Source: <https://github.com/VilnaCRM-Org/notification-service/issues/4>. Bundle: `specs/4-realtime-event-delivery-hub/`. Bounded contexts: `notification/event-stream` and `internal/cluster`.

## Executive Summary

The notification service becomes an open-source alternative to Mercure, written in Rust: a cluster of identical nodes that pushes events from the VilnaCRM event bus to browsers.

The frontend flow has three steps:

1. Read the catalog of subscribable event types over REST (`GET /api/event-types`) or GraphQL (`eventTypes`).
2. Subscribe to up to 100 event types over Server-Sent Events (`GET /api/events/stream`) or WebSocket (`GET /api/events/ws`).
3. Receive every event of a subscribed type as soon as it enters the service from the event bus, and resume after a reconnect with `Last-Event-ID` without loss or duplicate.

How it works, in terms a reader of the requirements needs:

- One node, the leader, reads the event bus through the `EventSource` port and appends each event to an event log in PostgreSQL. The log assigns a sequence number, which is the total order, the SSE `id` and the resume cursor.
- Every node relays new log rows to its own connected subscribers through an in-process hub. A PostgreSQL notification wakes the relay; a poll is the fallback. A subscriber that falls behind is not disconnected: it catches up from the log on its connection.
- The leader is chosen by a PostgreSQL lease with a term that grows on every change of holder. Raft is not used: the crate allow-list in the protected `architecture.toml` admits no Raft crate, and PostgreSQL is already the consistent store.
- The first `EventSource` adapter consumes an SQS queue (LocalStack in the local stack). The Kafka adapter and the schema repository are follow-ups; the port is their seam.
- The clients are browser frontends, usually served from another origin than the service. One allow-list of origins, `CORS_ALLOWED_ORIGINS`, decides which pages may use the HTTP routes and the WebSocket route; it allows no other origin by default (FR-28).
- The background work of a node (seed, listener, relay, election, ingestion, pruning) runs as supervised loops: a round that hangs is cut and retried, and a node that loses a loop leaves service instead of keeping clients it no longer serves (FR-29).

The code, the API and the table of the example context `company-subdomain/some-module` stay unchanged; its migration test is narrowed to its own table, and the two tests of `service migrate` that count migrations read the count from the embedded migrator, because the new migrations join the same set. Subscriber authorization is out of scope, so until it exists the service must carry only events that are safe for every client.

## Functional Requirements

Conventions used below:

- A problem is the RFC 9457 document of `shared_application::http::Problem`, media type `application/problem+json`.
- A parameter that cannot be parsed is answered with 400, type `about:blank`, and the parser text as `detail`. A parsed value that breaks a constraint is answered with 422, type `/problems/validation-failed`, and one `violations` entry (`propertyPath`, `message`, `code`) per broken constraint. This is the behaviour of `ValidatedQuery` in the example handlers.
- An event type name has 1 to 128 characters and matches `^[a-z][a-z0-9]*([._-][a-z0-9]+)*$`.
- A cursor is a sequence number written as a decimal unsigned 64-bit integer.

### Catalog

**FR-1 REST catalog.** `GET /api/event-types?page=&itemsPerPage=` returns 200 with a JSON array of `{"name": "<event type>"}`, sorted by name ascending in byte order (the names are ASCII, so `order-paid` comes before `order.paid` and `order_paid`, whatever the locale of the database). `page` is 1 or greater, default 1; `itemsPerPage` is 1 to 100, default 30. A page after the last one returns `[]`. `page=abc` returns 400; `page=0`, `itemsPerPage=0` and `itemsPerPage=101` return 422 with a violation on `page` or `itemsPerPage`. The operation is in the OpenAPI document and its committed snapshot, with the 200, 400, 422 and default problem responses.

**FR-2 GraphQL catalog.** The query `eventTypes(itemsPerPage: Int! = 30, page: Int! = 1): [EventType!]!` with `type EventType { name: String! }` (both arguments non-null with a default, the form of the committed schema) returns the same page as FR-1 for the same arguments, through the same query handler. The limits of FR-1 apply; a violation is a GraphQL error built from the same 422 problem. The query is in the committed GraphQL snapshot.

**FR-3 Catalog registration.** An event type is in the catalog when (a) it is listed in `EVENT_TYPES` at node start, or (b) an event of that type was ingested. Registration is idempotent: a type registered twice, or by two nodes at once, appears once. Every node registers the types of `EVENT_TYPES` as soon as it reaches the database: a node that starts while the database is down starts all the same and retries until the first success. A start with an invalid name in `EVENT_TYPES` fails with exit status 2 and names the variable, never its value.

> Assumption: a catalog entry is never removed in this issue. Removal needs the schema repository, which is a follow-up.
>
> Assumption: a client may subscribe to a well-formed type that is not in the catalog. The catalog is informative, as in Mercure, and a catalog check would add a database read to every subscription.

### Subscription over SSE

**FR-4 Open an SSE stream.** `GET /api/events/stream?types=<a,b,...>` answers 200 with `content-type: text/event-stream` and keeps the response open. `types` is required: a comma-separated list of 1 to 100 event type names; a repeated name counts once. The stream delivers every event of a listed type and no event of another type. The response head also carries `cache-control: no-cache` and `x-accel-buffering: no`, so that a proxy in front of the service does not hold frames and keep-alives back. A node that is starting, at its cap or shutting down answers with the 503 problem of FR-23 and opens no stream.

> Assumption: the parameter is the comma-separated `types`, not `?type=<name>` as the issue text says. One parameter covers one and many types, and it is the same on both transports.

**FR-5 SSE frame.** Each event is one frame with three fields: `id` is the sequence in decimal, `event` is the event type, `data` is the event data. Data that holds line breaks is written as one `data:` line per line, as the SSE format requires, so the client reads the text with every line break as a line feed: `\r\n` and a lone `\r` arrive as `\n`, because the SSE format cannot carry a carriage return (the WebSocket frame of FR-8 carries the text unchanged). Frames of one stream have strictly increasing ids, also after the connection fell behind and caught up from the log (FR-22).

**FR-6 SSE keep-alive.** When no frame was written for `STREAM_KEEP_ALIVE` (default 15 s), the server writes an SSE comment line. A comment carries no `id` and does not change the client's last event id.

### Subscription over WebSocket

**FR-7 Open a WebSocket.** `GET /api/events/ws[?types=<a,b,...>][&lastEventId=<n>]` upgrades to WebSocket (101). `types` is optional here: 0 to 100 names, with the rules of FR-4. A connection without types stays open and receives events after a run-time subscribe (FR-9). Every refusal is answered before the upgrade, with a problem and without a socket: invalid parameters with the problems of FR-13, a node that is starting, at its cap or shutting down with the 503 of FR-23, a handshake from an origin that is not allowed with the 403 of FR-28, and a request that is not a valid WebSocket upgrade with the 4xx status of the upgrade rejection.

> Assumption: `types` is optional on the WebSocket route because criterion 3 lets the client subscribe at run time; it stays required on the SSE route, which has no other way to name types.

**FR-8 Server frame.** Each event is one text frame `{"id":"<sequence>","type":"<event type>","data":"<text>"}`. `id` is a JSON string holding the decimal sequence; `data` is the event data as a JSON string. The frame is valid JSON for any UTF-8 data, including quotes, backslashes, control characters and characters outside the Basic Multilingual Plane.

**FR-9 Client commands.** A text frame `{"action":"subscribe","types":[..]}` adds the types to the connection's set; `{"action":"unsubscribe","types":[..]}` removes them. Both take 1 to 100 distinct names; a repeated name counts once. A valid command is not answered. After a subscribe, the events of the added types that the node relays from then on are delivered: those with a sequence above the position the node had relayed to when it handled the command and above the position the connection itself had reached. After an unsubscribe, no later event of the removed types is delivered, also not one that was already queued for the connection or read from the log for it. A command is handled between two log reads of the connection, never while one is in flight, so a command sent during a replay (FR-11, FR-22) takes effect during that replay and does not interrupt or repeat a read. Subscribing to a type already in the set and unsubscribing from a type not in the set are no-ops. The set never exceeds 100 types, and it may become empty: a connection that unsubscribed from its last type stays open.

> Assumption: a run-time subscribe starts at the position of the node and does not replay, also not when the connection later falls behind and catches up from the log (FR-22). Replay belongs to the connection request (FR-11), which is where the cursor is given.

**FR-10 Error frame and ping.** A frame that is not a valid command (not JSON, unknown `action`, an unknown member, missing or empty `types`, an invalid name, more than 100 distinct names, a set that would exceed 100 types, a binary frame, a text frame larger than 16 384 bytes) is answered with one text frame `{"error":"<reason>"}`. The subscription set is unchanged and the connection stays open. A message or a single frame larger than 32 768 bytes is not answered and ends the connection without a close frame; a frame that declares more than that is refused when its header is read, before its payload is buffered. The server sends a WebSocket ping every `STREAM_KEEP_ALIVE`, also during a replay, and answers a client ping with a pong. A close frame from the client is answered with a close frame and ends the subscription. The server itself closes a WebSocket with code 1001 at shutdown (FR-24) and with code 1011 when the log cannot be read during a replay (FR-11); after its own close frame it waits up to 1 s for the close frame of the client.

> Assumption: the size limit of a command is a constant, 16 384 bytes, and not `HTTP_MAX_BODY_BYTES`: the largest valid command, 100 names of 128 characters, takes 13 135 bytes, so there is nothing to tune, and the variable would refuse valid commands at its lower bound and admit 20 MiB per message at its upper bound. The transport limit for a message and for a frame is twice the command limit, and the read buffer of a connection is 4 096 bytes. No new variable is needed.

### Resume

**FR-11 Replay, then live.** A subscription that carries a cursor receives every retained event of its types with a sequence above the cursor, in sequence order, then live events, with no duplicate and no gap between the two phases. The cursor is the `Last-Event-ID` request header or the `lastEventId` query parameter on both routes; when both are present the header wins. A subscription without a cursor receives live events only. A cursor of `0` replays every retained event of the types. A cursor above the latest sequence is treated as the latest sequence. The replay is read inside the stream, in bounded pages (NFR-3, NFR-9): a subscription request is answered without a database read, and when the log cannot be read during a replay the stream ends (SSE: the response ends; WebSocket: close code 1011) and the client retries with its last id.

> Assumption: both routes accept both carriers. A browser `EventSource` sends the header by itself on reconnect; a browser WebSocket cannot set headers, so it uses the query parameter.
>
> Assumption: when the cursor is older than the retention window the replay starts at the oldest retained event and the loss is not signalled. A gap signal is a follow-up.

**FR-12 Retention pruning.** The leader deletes log rows recorded more than `EVENT_RETENTION` ago (default 1 h). Pruning never deletes a younger row and never reuses a sequence. It runs once a minute and removes the oldest expired rows first, in batches of at most 200 rows that each commit on their own, at most 1 000 000 rows per round. A backlog that is larger (the retention was lowered, or no node led for a long time) is removed over several rounds; no statement grows with the backlog, so pruning cannot fail for good once a backlog exists. Followers do not prune, so a cluster without a leader does not prune.

### Validation

**FR-13 Problems for invalid subscription input.** Both streaming routes answer invalid input with a problem and open no stream:

| Input | Status | Violation `propertyPath` |
| --- | --- | --- |
| `types` missing on the SSE route | 400 | none |
| `types` empty, or holding an empty name | 422 | `types` |
| an event type name that breaks the pattern or the length | 422 | `types` |
| more than 100 distinct names | 422 | `types` |
| `Last-Event-ID` or `lastEventId` that is not a decimal unsigned 64-bit integer (text, negative, overflow) | 400 | none |

The `detail` of a 400 names the parameter or header. The `code` of a violation on `types` is `required` (the list is empty or holds an empty name), `length` or `pattern` (a name that is not an event type) or `max_items` (more than 100 distinct names). An invalid name is never echoed in a log entry. The limit of 100 counts distinct names on both routes and in the commands of FR-9.

> Assumption: a malformed cursor is a 400 because it cannot be parsed, which is the existing convention for `page=abc`; the type list parses as text, so its faults are constraint violations and return 422.

### Ingestion

**FR-14 `EventSource` port.** Ingestion depends only on the domain port `EventSource` (receive a batch of inbound messages, acknowledge them). No domain or application crate names SQS. Replacing the adapter touches the infrastructure crate and the composition root only.

**FR-15 SQS adapter and envelope.** When `EVENT_QUEUE_URL` is set, the adapter long-polls that queue (batch of at most 10, wait 5 s). The envelope is: message attribute `event-type` (required, an event type name), `event-id` (optional UUID; default the SQS `MessageId`, which a redelivery keeps), `event-time` (optional RFC 3339 time in UTC, written with the suffix `Z` or `+00:00`, from the year 1970 to the year 9999; default the `Clock` time at receipt; kept to the microsecond); the message body is the event data, opaque UTF-8 text of 1 to `EVENT_MAX_DATA_BYTES` bytes (default 65536) that holds no U+0000. The size limit is a rule of ingestion only: lowering `EVENT_MAX_DATA_BYTES` does not affect events already stored, which are relayed and replayed until retention removes them. Acknowledgement is `DeleteMessageBatch`. Every receive asks for a visibility timeout of 30 s, whatever the queue is configured with, so a message that was received and not acknowledged is delivered again 30 s after that receive. When `EVENT_QUEUE_URL` is unset the node never ingests and never campaigns for the lease (FR-19), and still serves the catalog, subscriptions and relay.

**FR-16 Invalid messages.** A message with a missing or invalid `event-type`, an `event-id` (or defaulted `MessageId`) that is not a UUID, an `event-time` that is not an RFC 3339 time in UTC (a time with another offset than `+00:00`, such as `+02:00`, included) or a body that is empty, holds U+0000 or exceeds the size limit is not appended. It is logged once at `warn` with the SQS message id and the reason, without the body and without the attribute values, and it is acknowledged so that it does not block the queue. Valid messages of the same batch are processed normally.

> Assumption: an invalid message is dropped after the log entry. A dead-letter queue is a deployment setting of the queue (redrive policy) and a follow-up for the service.
>
> Assumption: a body must hold at least one byte and no U+0000. PostgreSQL `text` cannot store U+0000, so such an event could never be appended and would block its batch on every redelivery; an SSE event without a `data:` line is dropped by browsers. SQS itself refuses an empty body, LocalStack does not, so the service checks the rule.
>
> Assumption: `event-time` is accepted in UTC only. The application layer may use `humantime` and no other time parser (the protected crate allow-list), and `humantime::parse_rfc3339` of the locked version 2.4.0 reads the suffix `Z` and the literal `+00:00` and refuses every other offset (`src/date.rs`: the text must end with `Z` or `+00:00`).

**FR-17 Leader-only, idempotent ingestion.** Only the node whose status is leader receives from the source. A batch is appended to the log and its types are registered in the catalog (FR-3) before it is acknowledged. An event whose id is already in the log is not appended again, gets no new sequence, is delivered to no subscriber a second time, and is acknowledged. This holds while the row of the first delivery is retained: a redelivery comes 30 s after the receive (FR-15), and the shortest `EVENT_RETENTION` is 1 minute, so one failed acknowledgement never stores an event twice. Only a message that is still redelivered after its row was pruned (its acknowledgement kept failing for longer than `EVENT_RETENTION`) is stored and delivered a second time; `docs/operations.md` states that `EVENT_RETENTION` must exceed the redelivery horizon of the queue (30 s times the receive count of its redrive policy). A batch in which events were skipped because their id was stored leaves a trace: one `info` entry with their number (NFR-15), so that a producer that reuses an event id can be found. When the append fails, nothing of the batch is acknowledged and the bus redelivers it.

### Cluster

**FR-18 Cross-node fan-out.** With two or more nodes on one database, an event ingested by any node is delivered to the matching subscribers of every node. Each node keeps a cursor, reads the log after it when the signal fires (PostgreSQL `LISTEN` on channel `notification_events`) or when `EVENT_RELAY_POLL_INTERVAL` elapses (default 1 s), and publishes the rows to its hub in sequence order. A lost notification or a broken listener connection delays delivery by at most one poll interval and loses nothing. A node starts its cursor at the latest sequence; older events reach a client only through replay (FR-11). A node accepts subscriptions once its relay has read that start position; until then it answers every subscription request, with or without a cursor, with a 503 problem whose `detail` is `the node is starting`, so no subscription can miss an event that is committed around the start of the node. At an ordinary start this lasts for one database read; on a node that starts without the database it lasts until the first relay round after the database is back.

**FR-19 Leader lease.** One lease row names the leader. Each node that has an event source (`EVENT_QUEUE_URL` is set) campaigns in rounds, with a pause of `CLUSTER_RENEW_INTERVAL` (default 3 s) after each round; a node without one never calls the lease store and is always follower, so it can never hold the lease and keep the nodes that can ingest from leading. In a campaign the holder renews, another node acquires only when the lease has expired by the database clock (`CLUSTER_LEASE_TTL`, default 10 s). At any instant at most one node holds an unexpired lease. The term increases by exactly 1 when the holder changes and is unchanged by a renewal. A node whose election round fails or is cut after one `CLUSTER_RENEW_INTERVAL` becomes follower at once; a leader that cannot reach the lease store is therefore follower no later than three renew intervals after the database time of its last renewal, which the rule of FR-25 (`3 * CLUSTER_RENEW_INTERVAL <= CLUSTER_LEASE_TTL`) puts at or before the expiry of its lease.

**FR-20 Failover and release.** When the leader stops without releasing (crash, partition), another node that has an event source becomes leader no later than `CLUSTER_LEASE_TTL` plus one `CLUSTER_RENEW_INTERVAL` plus twice the answer time of a lease call after the stop (13 s with the defaults and a healthy database; never more than `CLUSTER_LEASE_TTL` plus three renew intervals, 19 s with the defaults, because a lease call is cut after one renew interval), and ingestion continues from the bus with no lost event. The messages that the stopped leader had received and not acknowledged are delivered again 30 s after their receive (FR-15), which can be later than the takeover. On graceful shutdown the leader releases the lease, and another node that has an event source becomes leader within one `CLUSTER_RENEW_INTERVAL` plus twice the answer time of a lease call (3 s with the defaults and a healthy database; never more than three renew intervals, 9 s with the defaults; when the release fails, the bound of a crash applies). That bound is for a node that stops as leader. A node that is stopped as follower makes no lease call at its stop; if the campaign that the stop cancelled had just taken the lease in the database, that lease ends by its expiry, and the bound of a crash applies. Failover of ingestion needs `EVENT_QUEUE_URL` on at least two nodes: with one such node nobody takes over while it is down, and with none there is no leader and no ingestion. While the lease store is unreachable no node leads, and the bounds count from the moment it answers again.

> Assumption: criterion 6 says "within the configured lease time". The exact bound is the TTL (expiry) plus one renew interval (the pause before the next campaign of a follower) plus the answer time of the two lease calls around that pause: 13 s with the defaults when the database answers in milliseconds, and at most the TTL plus three renew intervals; the PRD states that bound.

**FR-21 Cluster status.** `GET /api/cluster` returns 200 with `{"nodeId": "<uuid>", "role": "leader" | "follower", "leader": "<uuid>" | null, "term": <integer>}`. It reports this node's view after its last election round: `leader` is `null` and `role` is `follower` when the last round failed or none has finished; `term` is the last term seen, `0` before the first successful round. A node without an event source runs no election round (FR-19), so it answers `role` `follower`, `leader` `null` and `term` `0` for the life of the process; the leader is read from a node that campaigns. The operation is in the OpenAPI document and its snapshot. `NODE_ID` sets the node id; when unset, a UUIDv7 from `UuidGenerator` is used for the life of the process.

### Protection and lifecycle

**FR-22 Slow consumers.** Each subscriber has a queue of `SUBSCRIBER_BUFFER` events (default 256). Publishing never waits: when a subscriber's queue is full, the node stops queueing for it. The subscriber is not disconnected: it gets the frames already queued, then the events it missed, read from the log by its position in bounded pages, in order and without duplicate, on the same connection, and then live events again. Other subscribers, the relay and ingestion are not delayed. The service ends a connection because of its client in one case only: a client whose connection accepts no data for `STREAM_KEEP_ALIVE` is disconnected, without the frames still queued for it, an SSE client without an end of its stream and a WebSocket client without a close frame, and it resumes by reconnecting with its last id (FR-11). "Accepts no data" means that nothing got through to the client for that time: it has vanished, or it reads nothing and its receive window is closed. A client that reads slowly is never disconnected. Two bounds of the same length enforce it: the service sets a send bound on every accepted connection, by which the operating system ends a stalled connection of either transport about `STREAM_KEEP_ALIVE` after it stalled, and a write to a WebSocket has a deadline. The send bound acts on HTTP/1.1 connections, on Linux, where the service runs. An SSE stream on an HTTP/2 connection that is stalled by its own flow control while the connection stays alive is not ended by it and keeps its slot (FR-23) and its buffers (NFR-9) until its client leaves (Product Scope, out of scope).

> Assumption: a full queue no longer disconnects the subscriber, as the first draft of this requirement did. The relay hands a page of events to the queues faster than any client task can take them, so one relay round with more than `SUBSCRIBER_BUFFER` events of a type (a backlog after a failed round, the poll fallback, a burst) would disconnect every subscriber of that type at once, however fast the clients are, and all of them would reconnect with a cursor. Catching up on the connection costs the same log reads and no reconnect. Criterion 8 of the issue reads "its buffer is bounded and it is disconnected when it lags past the buffer". Its purpose (a slow or stalled client never blocks other clients or ingestion) and the bounded buffer hold unchanged; the disconnection at the buffer limit is replaced by the catch-up, and the only client the service itself disconnects is one that takes no data at all. The deviation from the wording of the criterion is listed under the traceability table.
>
> Assumption: the service sets a socket-level send bound (`TCP_USER_TIMEOUT`, with the value of `STREAM_KEEP_ALIVE`) on every accepted connection. The first revision of this requirement left a stalled SSE client to the send timeout of an edge proxy; the bound was taken after the validation. The reason: the service is unauthenticated and may run without an edge proxy, so a client that stops reading must not hold a slot, its buffers and a shutdown for ever, and two of the three checks of the validation called the bound mandatory. Once an SSE client stops reading and the write buffer of the HTTP server is full (about 408 KiB), the server stops asking the response for frames, so nothing in the application runs for that connection and only the transport can end it. The cost is one dependency in the composition root and three limits, each stated where it applies: an HTTP/2 stream that is stalled by its own flow control is not covered (Product Scope, out of scope), a client that stalled shortly before a shutdown can still force it (FR-24), and the entry `subscriber evicted` is best effort (NFR-15). The bound has no variable of its own: a value below a keep-alive period would cut clients on a short network pause, so it is the keep-alive period. A send timeout of the edge proxy is a recommendation from now on and no longer a prerequisite (FR-27).

**FR-23 Subscriber cap.** When the node already has `MAX_SUBSCRIBERS` subscribers (default 100000), a new SSE or WebSocket request is answered with a 503 problem (type `about:blank`, `detail` `the node is at its subscriber capacity`) and no stream or upgrade. The cap counts connections: a slot is taken from the request until the connection of the subscriber has ended, and a subscriber that fell behind (FR-22) keeps its slot. A client that accepts no data keeps its slot until it is disconnected, about `STREAM_KEEP_ALIVE` after its connection stalled (FR-22); a stalled stream on an HTTP/2 connection keeps its slot until its client leaves (Product Scope, out of scope). The same 503 shape with its own `detail` answers a request on a node whose relay has not started (`the node is starting`, FR-18) and on a node that is shutting down (`the node is shutting down`, FR-24); when more than one applies, the answer is that of shutting down, then of starting, then of the cap. A 503 is safe to retry on any node; a browser `EventSource` does not retry it by itself (NFR-5). The cap is per node and not per client: one client can occupy every slot of a node until limits per client exist (NFR-14).

**FR-24 Graceful shutdown.** On SIGTERM or SIGINT the node refuses new connections at once, as today. Then, in this order, it:

1. stops the background loops: an ingest batch in progress and a lease renewal in flight finish first, and every other round and every pause ends at once, also while the database or the queue does not answer;
2. releases the lease if it is leader (a follower makes no lease call);
3. closes the hub, which ends every SSE response and closes every WebSocket with code 1001, each after the frames already queued for it; from then on a subscription request gets the 503 `the node is shutting down` (FR-23);
4. waits at most 2 s until these connections have ended;
5. drains HTTP as today.

The whole sequence runs inside `SHUTDOWN_GRACE_PERIOD`, and the exit status is 0 when it ends in that time. An ingest batch in progress is either appended and acknowledged or not acknowledged at all. An idle node stops within milliseconds, also with every dependency down, as before this change. Two kinds of client can outlast step 4: a WebSocket client that takes no data is cut off without its close frame when the 2 s end, and the exit status stays 0; an SSE client that takes no data keeps the HTTP drain open until the send bound of the service ends its connection, about `STREAM_KEEP_ALIVE` after it stalled (FR-22). A client that stalled earlier than that before the signal is gone already. For a client that stalled within the last `STREAM_KEEP_ALIVE` before the signal, the exit status is 0 when its connection ends inside the grace period and 1 when the grace period ends first, as today for any request that does not finish. With the defaults (`STREAM_KEEP_ALIVE` 15 s, `SHUTDOWN_GRACE_PERIOD` 10 s) that is a client that stalled less than about 5 s before the signal; a deployment in which exit status 0 matters in that case too sets `STREAM_KEEP_ALIVE` below the grace period. A stalled stream on an HTTP/2 connection holds the drain to the end of the grace period (Product Scope, out of scope). When a batch or a renewal that a dependency does not answer outlasts the grace period, the node is forced down in the same way, and a lease that was not released ends by its expiry (FR-20). The same sequence runs when a background loop died, and the exit status is then 1 (FR-29).

> Assumption: the WebSocket close codes are 1001 (going away) for shutdown and 1011 (internal error) when the log cannot be read during a replay, both from RFC 6455, so a client can tell an ended subscription from a lost connection. Code 1013 of the first draft is not used: a subscriber that falls behind is no longer disconnected (FR-22), and a client that takes no data gets no close frame at all.
>
> Assumption: new connections are refused from the signal on, before the loops stop, as today, so that a deployment does not keep routing connections to a node that is leaving. The order of this requirement governs the work that is already there: the loops, the lease, the hub and the end of the drain.
>
> Assumption: the wait of step 4 has a bound of its own, 2 s, which is a constant. An upgraded WebSocket is outside the HTTP drain, so without the wait its queued frames and its close frame would race with the end of the process. A client that answers the close frame is gone within milliseconds and one that stays silent after it costs 1 s (FR-10); a client that takes no data at all would end only by the send bound or by its write deadline, each `STREAM_KEEP_ALIVE` long (15 s by default, above the default grace period), which the shutdown does not wait for. No deployment has to tune the bound, so it is not a variable.

### Configuration, load test and documentation

**FR-25 Configuration.** The twelve variables below are read once in the composition root and validated at start; `service check-config` applies the same rules. An invalid value fails with exit status 2 and a message that names the variable and the rule and never prints its value. Each variable has a row in `docs/environment.md`. What the validation changed in the meaning of a variable: `SUBSCRIBER_BUFFER` is the number of events a subscriber may lag before it leaves live delivery and catches up from the log (FR-22); `MAX_SUBSCRIBERS` counts open connections (FR-23) and is sized by the memory of the node (NFR-9); `STREAM_KEEP_ALIVE` is also the time after which a connection that accepts no data is ended, as the send bound of every accepted connection and as the write deadline of a WebSocket (FR-22), so a deployment in which a shutdown must end with status 0 also with a stalled client sets it below `SHUTDOWN_GRACE_PERIOD` (FR-24); the existing `DATABASE_MAX_CONNECTIONS` sizes the pool of the requests, of which half may serve replays (NFR-12, NFR-21); the existing `HTTP_MAX_BODY_BYTES` does not apply to WebSocket messages, whose limits are constants (FR-10).

### Browser access and supervision

**FR-28 Browser origins.** `CORS_ALLOWED_ORIGINS` (FR-25) names the origins whose pages may use the service. It is one allow-list for the HTTP routes, where the browser enforces it through the CORS headers, and for the WebSocket route, where the service enforces it itself, because a browser applies no CORS rule to a WebSocket.

| `CORS_ALLOWED_ORIGINS` | Catalog, GraphQL, SSE and every other HTTP route | WebSocket handshake (a request that carries `Sec-WebSocket-Key`) |
| --- | --- | --- |
| unset (default) | exactly as before this change: no response carries a CORS header, and an `OPTIONS` request gets the 405 problem, or the 404 problem for an unknown path. A browser lets only pages of the service's own origin read the answers | answered with the 403 problem (`detail` `the origin is not allowed`) when it carries an `Origin` header; no subscriber is registered |
| a list of origins | a request whose `Origin` is on the list gets `Access-Control-Allow-Origin` with that origin on every response of every route, the problem responses (404, 405, 422, 500, 503) and the SSE response head included; every response carries `Vary: Origin`; a request of another origin is served without `Access-Control-Allow-Origin`, and its browser hides the answer from the page | accepted when its `Origin` is on the list, else the 403 problem |
| `*` | `Access-Control-Allow-Origin: *` on every response | accepted from every origin |

With a list or `*` the service answers every `OPTIONS` request itself, also for an unknown path, with 200, an empty body and the headers of a preflight answer: the methods `GET` and `POST`, the request headers `Content-Type` and `Last-Event-ID` and a max age of 600 s. The answer carries `Access-Control-Allow-Origin` only for an allowed origin, so only the preflight of such an origin is approved. No credentials are allowed and no response header is exposed. A request without an `Origin` header is never restricted, on any route: command-line clients, other services and the load test send none. An entry is compared byte for byte with the `Origin` header, which is why FR-25 accepts only the form a browser sends. The list is a rule for browsers and not an authorization (NFR-13): it decides which sites may embed the service, and every event stays readable by any client that reaches the service.

> Assumption: the service answers CORS itself, with an allow-list that allows nothing by default, instead of leaving the headers to the edge proxy as the template does. Browser frontends are the clients of this issue and they call VilnaCRM services from other origins; the local stack has no proxy, so without the list a page of another origin could use neither the catalog nor GraphQL nor the SSE route there, while the pages of every site could use the WebSocket route.
>
> Assumption: the same list guards the WebSocket handshake. A list for the HTTP routes alone would be no rule at all: a page of any site could read the same events over the WebSocket route.
>
> Assumption: with the variable unset a WebSocket handshake that carries `Origin` is refused, also from a page of the service's own origin. Behind a proxy the service does not know its public origin, so "same origin" cannot be decided reliably; an operator who serves the frontend from the origin of the service lists that origin. The HTTP routes need no such entry, because a browser allows same-origin requests by itself.
>
> Assumption: when the variable is unset the CORS layer is absent, not installed with an empty list. An installed layer answers every `OPTIONS` request with 200, which would change two existing status codes (NFR-20) and the answers that the Schemathesis gate judges.
>
> Assumption: a page of any site can still make the browsers of its visitors open SSE requests without reading the answers, because a request that needs no CORS approval cannot be told apart from any other client. That is the limit per client which this issue leaves to the edge proxy (NFR-14); the list does not claim to prevent it.

**FR-29 Supervision of the background loops.** A node runs its background work as six supervised loops: catalog seed, listener and relay on every node, and election, ingestion and pruning on a node that has an event source (FR-19).

- A failed round does not end its loop: it is logged once (NFR-15) and the next round follows after the pause of that loop.
- A round that does not return is cut and counts as a failed round. A seed, relay or prune round and the processing of a received batch are cut after a limit derived from the configuration: twice `DATABASE_ACQUIRE_TIMEOUT`, plus six times `DATABASE_STATEMENT_TIMEOUT`, plus `SQS_OPERATION_TIMEOUT` and the 5 s of the long poll, which is 41 s with the defaults. An election round is cut after one `CLUSTER_RENEW_INTERVAL` (FR-19). The cut loses nothing: the relay continues from its cursor, pruning from the oldest expired row, and a batch that was cut is either not acknowledged or, when its append had committed, recognised by its event ids at the redelivery (FR-17).
- A loop that dies (a panic of its task) does not leave a node in service that keeps its clients and delivers nothing. The node writes `background task failed` (`error`, with the name of the loop) when the loop dies, runs the shutdown sequence of FR-24 and exits with status 1: its clients get the end of their stream or close code 1001 and resume on any node, the lease is released, and the orchestrator starts the node again.

> Assumption: a dead loop ends the node; it is not reported through a readiness probe and not restarted in place. The health report keeps its three probes (NFR-15); a failed probe would take the node out of the load balancer but leave its open streams on a node that delivers nothing, and only the end of the process makes those clients reconnect. Restarting the loop inside the process would hide a defect: the lint policy leaves no panicking path in the code of the service, so a panic comes from a dependency in a state nobody has analysed.
>
> Assumption: a hung round is cut and retried, and does not end the node. During a database outage every node sees failing or hanging rounds, and NFR-11 wants the open streams to stay.
>
> Assumption: the limit of a round is derived and is neither a variable nor a constant. `DATABASE_STATEMENT_TIMEOUT` may be anything from 1 ms to 24 d, so no constant fits every accepted configuration; the sum is the longest time that the one round which cannot be resumed, the processing of a batch, may take while every call is still answered, so a batch that the database and the queue still answer is never cut.

## Non-Functional Requirements

### Performance

**NFR-1 Capacity.** One node on the reference machine (4 vCPU, 8 GiB) holds 10 000 concurrent SSE or WebSocket subscribers with a p99 fan-out latency, measured from the log append to the socket write, below 100 ms at 100 events/s. This is a design target and not a merge gate, and this change does not measure it (Product Scope, out of scope). What this change delivers and tests are the structural conditions of the target: NFR-2, NFR-3, NFR-9, NFR-10 and a hub test that hands one event to 10 000 subscriber queues of its type. With every subscriber on one type the target load is 1 000 000 frames per second, which a load generator on the node's own machine cannot produce. The K6 trend `event_delivery_latency` of FR-26 measures another interval, from the publish on the bus to the receipt by a WebSocket client; it contains the interval of this requirement plus the bus leg and the lag of the generator, so a value below 100 ms would prove the target and a higher one does not disprove it.

**NFR-2 Publish cost.** The cost of publishing one event is proportional to the number of subscribers of its type, never to the number of connections. On the live path a frame is encoded once per event and shared by all its subscribers, and an event whose type has no subscriber on the node is not encoded at all. A replayed event is encoded for its one connection when it is written.

**NFR-3 No database read on the live path.** A connected client causes zero per-event database reads. The node reads the log once per relay page for all its clients, never once per client; a client reads the log only during its own replay (after a request with a cursor, or after it fell behind, FR-22), in bounded pages: each read covers at most 10 000 log positions and returns at most 500 events and 1 MiB of event data plus the one event that reaches that budget. The cost of a read does not grow with the size of the log or with the types asked for. A replay starts no lower than the oldest retained event, so the number of its reads is bounded by what the log retains, at most one read per 10 000 retained positions when none of its types occurs, and not by the cursor of the client or by the age of the deployment: a cursor of `0` on a log that has pruned for months costs no more than one on a new log. The next page is read only when the client has taken the frames of the last one, so a slow client reads the log slowly and a client that reads nothing causes no read. A subscription request itself reads nothing (FR-11).

**NFR-4 Smoke budget.** The K6 smoke profile of FR-26 passes within its p99 budget, within its delivery ceiling (`deliveryThreshold`, the p99 of `event_delivery_latency`) and within the existing success-rate threshold of the checks (above 99 %).

### Availability and failover

**NFR-5 Any node serves any client.** Nodes are interchangeable for the catalog and subscriptions. The cluster status is each node's own view (FR-21): a node without an event source does not name the leader. The loss of a node costs its clients one reconnect and no event within the retention window. A reconnect that reaches a node that is starting, at its cap or shutting down is answered with a 503 (FR-23) and is repeated; a browser `EventSource` does not repeat a request that was answered with a status other than 200, so the page creates a new `EventSource` and passes the last id as `lastEventId` (FR-27). A node that can no longer serve does not stay in service: when one of its background loops has died it shuts down and exits with status 1, and its clients resume on any node (FR-29).

**NFR-6 Failover time.** When another node has an event source, a leader crash pauses ingestion for at most `CLUSTER_LEASE_TTL` plus one `CLUSTER_RENEW_INTERVAL` plus twice the answer time of a lease call (13 s with the defaults and a healthy database, never more than `CLUSTER_LEASE_TTL` plus three renew intervals, 19 s); a graceful leader stop for at most one `CLUSTER_RENEW_INTERVAL` plus twice that answer time (3 s, never more than 9 s with the defaults). The up to 10 messages that a crashed leader had received and not acknowledged are delivered again 30 s after their receive. Without a second node that has an event source nobody takes over (FR-20). Delivery of events already in the log is not paused by a leader change.

**NFR-7 No split leadership by clock skew.** Lease expiry is judged by the database clock only, so the clocks of the nodes cannot produce two lease holders. A node that held the lease and was paused past its expiry can at worst ingest one more batch; the result is still correct because the append is idempotent by event id (FR-17).

### Delivery guarantees

**NFR-8 Guarantees.** Ingestion from the bus is at-least-once and idempotent by event id while the row of the event is retained (FR-17). The log sequence is a total order, equal to commit order. Each subscriber receives the events of its types in sequence order, each at most once per connection. Across reconnects with the last received id, a client receives every event of its types exactly once within the retention window. No guarantee is given for a cursor older than the window.

### Resilience

**NFR-9 Bounded memory.** A subscriber holds at most `SUBSCRIBER_BUFFER` shared frame references, its type set of at most 100 names and, while it replays, one page of at most 500 events and 1 MiB of data plus one event; a replay never loads the retention window at once. A WebSocket holds, whatever its client sends, at most a read buffer of 4 096 bytes, one inbound frame and one inbound message of at most 32 768 bytes each, and a write buffer of the size of the largest event sent on it. An SSE response whose client does not read holds at most about 408 KiB of written frames plus one frame, for about `STREAM_KEEP_ALIVE`, after which its connection is ended (FR-22). The hub keeps an entry only for an event type that has a subscriber queue, so the names that clients subscribe to and leave again do not accumulate (a client may subscribe to any well-formed name, FR-3). The relay holds one page of at most 500 events at a time (at most 500 times `EVENT_MAX_DATA_BYTES` of data, 32 MiB with the default). A node holds at most `MAX_SUBSCRIBERS` connections, counted from the request until the connection has ended (FR-23), so the memory of a node is bounded by `MAX_SUBSCRIBERS` times these figures and `MAX_SUBSCRIBERS` is sized by the memory of the node: an idle connection costs about 6 KiB (WebSocket) or 20 KiB (SSE), so the default of 100 000 needs about 0.6 GiB for idle WebSockets and about 2 GiB for idle SSE streams. The production compose reference, whose memory limit is 256 MiB, therefore sets 5 000 (FR-25), and `docs/operations.md` gives the rule: the cap times 20 KiB stays below half of the memory limit. The other half is for the connections that hold more than an idle one: a connection that replays for a slow client holds its page, up to 1 MiB more, and an SSE response that is not read its 408 KiB, and a deployment that expects many slow clients with a cursor counts them with these figures. At most max(1, `DATABASE_MAX_CONNECTIONS` / 2) replay reads run at one time (NFR-21); that number is also the rate at which subscribers that fell behind catch up, so it grows with `DATABASE_MAX_CONNECTIONS`.

**NFR-10 Back-pressure isolation.** No operation on the publish path waits for a client. A subscriber that cannot keep up affects only itself: it is taken off live delivery and reads the log at its own pace (FR-22). A connection that accepts no data is ended about `STREAM_KEEP_ALIVE` after it stalled and holds only its own slot and buffers until then (FR-22, NFR-9). The relay, other subscribers and ingestion keep their pace. A relay round that carries more events than a queue holds disconnects nobody.

**NFR-11 Database outage.** While PostgreSQL is unreachable: open connections stay open and get keep-alives; no new event is delivered; every node is follower and ingestion stops, with messages left on the bus; the catalog answers with the 500 problem; on a node whose relay had started, a subscription without a cursor is accepted, and a subscription with a cursor is accepted and its stream ends when its first log read fails (SSE: the response ends without a frame; WebSocket: close code 1011), after which the client retries; a replay that is running when the outage begins ends the same way; a round of a background loop that fails or hangs is logged, cut after its limit and tried again, and no node leaves service because of the outage (FR-29); a node that started during the outage answers every subscription request with the 503 problem `the node is starting` until its relay has read its start position (FR-18). When the database returns, a leader is elected, ingestion resumes and each relay continues from its cursor (a node that started during the outage reads its start position then and had no subscriber before), so no event is lost. PostgreSQL high availability is a deployment prerequisite. An SQS outage pauses ingestion only; it is retried at the next round. The leader keeps the lease meanwhile, because the lease follows the lease store and not the queue: ingestion resumes when that node reaches the queue again, and no other node takes over (Product Scope, out of scope).

### Scalability

**NFR-12 Horizontal scale.** Nodes are stateless apart from their connections and their relay cursor; all shared state is in PostgreSQL. Adding a node adds subscriber capacity without configuration on the other nodes. Each node opens at most `DATABASE_MAX_CONNECTIONS + 4` database connections: the pool of the requests, three connections for the background loops and one listener connection (NFR-21). Ingestion throughput is that of one leader and does not scale with the node count.

### Security

**NFR-13 No subscriber authorization yet.** Any client that reaches the service can read the catalog and subscribe to any type. Consequence: the service must carry only events that are safe for every client, and it must not be exposed with private data on the bus. `SECURITY.md` and the protocol document say so. The allow-list of origins (FR-28) does not change this: it binds browsers only, and a client that sends no `Origin` header is never restricted. Follow-up: authorization with a JWT from the user-service OAuth server, and private topics.

**NFR-14 Input limits and secrets.** Every external input is bounded: 100 types per subscription, 128 characters per name, 64-bit cursor, 16 384 bytes per WebSocket command and 32 768 bytes per WebSocket message or frame (FR-10), `EVENT_MAX_DATA_BYTES` per event, 10 messages per bus batch, `MAX_SUBSCRIBERS` connections per node. What a client can make the node do is bounded as well: a replay read covers at most 10 000 log positions and returns at most 1 MiB plus one event (NFR-3), at most half of the request connections serve replays (NFR-21), an inbound frame never repeats a log read (FR-9), and the hub keeps no entry for a type without a subscriber (NFR-9). All SQL is parameterised. No log entry, problem or configuration error holds a secret, the value of a variable, event data, an event type name taken from a request or the queue URL's credentials. `make.check_security` and `make.secrets_scan` pass.

The service sets no limit per client in this issue: none on the connections per source address, none on the rate of WebSocket commands, none on the time a WebSocket may stay without a subscription. One client can therefore occupy every slot of a node (`MAX_SUBSCRIBERS`), after which the other requests get the 503 of FR-23. The edge proxy must limit the connections per client address; the template already leaves the number of connections to it for every route (`docs/architecture.md`, operational assumptions). `docs/operations.md` states this prerequisite and `SECURITY.md` the consequence (FR-27). Limits inside the service are a recorded follow-up (Product Scope, out of scope).

### Observability

**NFR-15 Structured logs.** One structured `tracing` entry with a fixed message is written for each case below. No entry contains event data, an event type name taken from a request or the value of a variable.

| Message | Level | Fields | Written when |
| --- | --- | --- | --- |
| `leadership changed` | `info` | node id, role, leader, term | an election round changed the role or the leader of the node |
| `lease store failed` | `warn` | the error chain | a lease call failed or was cut; the node is follower from then on (FR-19) |
| `subscriber evicted` | `warn` | transport, number of types, last sequence | a WebSocket was disconnected because a write to it missed its deadline (FR-22). This entry is best effort: the send bound of the operating system usually ends a stalled connection first, and that end writes no entry, for a WebSocket and for an SSE response alike |
| `subscribers fell behind` | `warn` | their number | once per relay page in which at least one subscriber fell behind (FR-22) |
| `subscription rejected` | `warn` | the reason: the `detail` of the 503 | a subscription request was refused because the node is starting, at its cap or shutting down (FR-23) |
| `duplicate events skipped` | `info` | their number | a processed batch held events whose id was already stored (FR-17) |
| `inbound message rejected` | `warn` | message id, reason | an invalid message of the bus (FR-16) |
| `event signal failed` | `warn` | the error chain | the listener could not be created or could not reconnect (FR-18) |
| `ingestion failed`, `relay failed`, `prune failed`, `catalog seed failed` | `error` | the error chain | once per failed or cut round of that loop (FR-29) |
| `background task failed` | `error` | the name of the loop | a loop died; the node then shuts down (FR-29) |

A healthy node is silent while it works: a node with an event source writes `leadership changed` once when it takes the lease, and a node without one writes none of these entries. The existing entries of `serve` (`listening`, `shutdown signal received`, `stopped` and the entry of a forced shutdown) keep their message, level and fields. The existing readiness report keeps its three probes; no probe is added.

### Isolation of the control plane

**NFR-21 Client load does not reach the loops.** What a client request drives and what the node itself drives use separate database connections. The catalog queries and the replay reads use the pool of the requests (`DATABASE_MAX_CONNECTIONS`); the election, the relay, ingestion, pruning and the catalog seed use three connections of their own; the listener has one more (NFR-12). Replay reads take at most max(1, `DATABASE_MAX_CONNECTIONS` / 2) of the request connections at a time and wait for their turn in arrival order, inside their stream and never inside a request, so the catalog and the readiness probe keep finding a connection. A flood of client reads (a reconnect storm after the loss of a node, many catalog requests) therefore cannot delay a lease renewal until the leader steps down and cannot stop live delivery; a request that finds no connection within `DATABASE_ACQUIRE_TIMEOUT` gets the 500 problem, and a replay waits for its turn.

> Assumption: the three connections of the loops and the share of the replays are constants. An operator sizes `DATABASE_MAX_CONNECTIONS` for the clients, and nothing in a deployment changes what the loops need. Measured by the validation on the pool of the template, 10 connections shared by everything: 30 replay requests per second delayed the lease renewals up to the acquire timeout, at which the leader steps down. With the separate connections and the bounded replays, 30 000 clients that reconnected within one second were all served while the renewals answered within 10 ms.

### Delivery guarantees

1. **Ingestion:** at-least-once from the bus. A message is acknowledged only after its event is in the log (or after it was judged invalid and logged). A redelivered event is recognised by its id and stored once, as long as its first row is retained: the bus redelivers after 30 s and the shortest retention is 1 minute (FR-17).
2. **Order:** the log sequence is the single total order for all types and all nodes. Sequences are unique and increasing; they may have gaps and are never reused.
3. **Live delivery:** every node delivers each log row to each of its matching subscribers at most once per connection, in sequence order, within one relay poll interval of the commit even when the notification is lost. A node accepts a subscription only once its relay has read its start position (FR-18), so no subscription can miss an event that is committed around the start of a node.
4. **Resume:** a client that reconnects to any node with the last id it received gets every later retained event of its types, in order, without duplicate, before live events.
5. **Retention:** events are kept for `EVENT_RETENTION` after they were recorded. A client away longer than that can miss events and is not told.
6. **Lagging client:** a subscriber more than `SUBSCRIBER_BUFFER` events behind is neither throttled nor disconnected; the node stops queueing for it and it catches up from the log on its connection, in order and without duplicate (guarantee 4 without the reconnect). A client whose connection accepts no data for `STREAM_KEEP_ALIVE` is disconnected and recovers through guarantee 4 (FR-22).
7. **Not guaranteed:** delivery to a client that never reconnects; delivery of a message the adapter judged invalid; order between events as produced on the bus (the order is that of ingestion); a single storage of a message that is still redelivered after its row was pruned (FR-17); a slot for a client while another client occupies the node (NFR-14); confidentiality between clients (NFR-13).
