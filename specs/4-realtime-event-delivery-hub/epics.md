# Epics and Stories: real-time event delivery hub (issue #4)

This file slices `architecture.md` of this bundle into stories for the one new context `notification/event-stream` and for the removal of PostgreSQL and of the example context. It adds no component: every file, type, constant, limit, route, variable, log message and problem text below is the one of `architecture.md` and `prd.md`. Where a story names a test list of the section "Test Strategy" of `architecture.md`, that list is binding for the story. A decision taken while slicing is a line `> Assumption:` in the story it affects, or below when it affects the whole file.

**How the stories run:**

- The stories run in waves. A story is ready when the stories of its "Depends on" line are done; the ready stories form one wave. One implementer works on each story of a wave, all in one working tree; a story marked "Maintainer" is never dispatched to the rust-implementer agent. One serialized verify step then runs the targets that need the shared Kafka broker (`make.integration_tests`, `make.tests_with_coverage`, `make.e2e_tests`, `make.mutation_tests_diff`), and each story is committed on its own through the hooks as `<type>(#4): story N.M <title>`.
- (i) Only the tree at the end of a wave has to compile and pass the lint and unused-dependency gates; a compile error or finding in a file of another story of the same wave is not a story's failure.
- (ii) `Cargo.lock` is regenerated by cargo, never edited by hand. A lock refresh never raises another crate's version (`make update` is not used).
- (iii) Two stories of a wave may each add their own lines to the same manifest, `lib.rs`, `http.rs`, `tests/support/src/lib.rs`, `.templatesyncignore`, `.env` or `docs/environment.md`. They never rewrite the same function, struct, test or section; the "Scope" list of a story names the lines it owns.
- (iv) A story uses only types that exist before its wave starts; a "Depends on" edge orders the two stories. An edge that only orders two stories that write the same file is called an "order" edge in the story text.
- Every story carries its own tests to the bar of the repository: 100 % line and function coverage of its code, both sides of every boundary, every error branch and every log entry asserted, every awaited call of a test inside `tokio::time::timeout`, paused tokio time wherever a timer is involved, and a scripted fake pends after its script. No story plans an `#[allow]`, a `#[mutants::skip]`, a `#[coverage(off)]`, a coverage or mutation exclusion, a lowered bar, or a protected-file edit that its title does not announce. An `#[expect(.., reason = "..")]` is used only where `architecture.md` names it (a test helper that reads `KAFKA_BOOTSTRAP_SERVERS` or opens a socket).
- The mutation run of a wave runs after the commits of the wave (`make.mutation_tests_diff` with `base_ref=<commit before the wave>`). A wave that changed production Rust and whose run names no mutant is not recorded as passed. A surviving or timed-out mutant is fixed by a further commit in the files of the owning story before the next wave.
- A dependency enters a member manifest in the story whose code first uses it; a workspace path entry is added at first use; a crate-private item is added by the story of its first caller.
- Every story that changes a route regenerates both contract snapshots in the same commit; every story that adds a variable adds it to `cli.rs`, `config.rs`, `docs/environment.md` and (when it has a default) `.env` together; every story that changes a file the template sync would restore adds it to `.templatesyncignore`.
- No story presents a latency, throughput or capacity number as measured. NFR-1 is a design target (decision D18); the K6 budgets are budgets.

**Approval of protected changes (decision D16).** The rust-implementer agent of the plugin never edits a protected path or the profile, and the plugin's self-check and publish step refuse a commit when a protected file differs from the merge base. So:

- Epics 1 and 2 change no protected file and need no entry of the preparatory pull request; the rust-implementer agent implements them first, in their order.
- Story 3.1 is the preparatory pull request. It holds every protected change the feature and the later removal need in the base branch: the four allow-list entries of `architecture.toml` and the two `required_directories` entries of `protected-config.toml`. It is requested from the maintainer in wave 1, lands on its own branch from `main` and is merged into `main` by the maintainer under the label `approved-config-change`; the edit is made by the maintainer or by a session with `ALLOW_PROTECTED_CONFIG_EDIT=1`, never by the rust-implementer agent. The feature branch then merges `main` (a merge commit, exempt from the subject rule in `scripts/check-commit-message.sh`), so its merge base holds the five changes and the protected-change checks of the plugin stay silent for the rest of Epic 3 and for Epic 4.
- Stories 3.2 to 3.8 and Epic 4 change no protected file; the rust-implementer agent implements them once the merge is done.
- Epic 5 (the removal) and story 6.1 run in an approved operator session (labels `approved-config-change` and `approved-breaking-change` on pull request #5, `ALLOW_PROTECTED_CONFIG_EDIT=1`), not in the plugin's implementer loop: from story 5.1 on the feature branch differs from its merge base in protected files, so every plugin stage ends ESCALATED by design and the operator continues by hand.

The first line of every story says which case applies and who implements it.

> Assumption: the envelope parser and the tail use case come after the preparatory pull request. `parse_event` (used by `TailEvents` and by the Kafka pages of `Subscription::step`) needs `serde_json` as a normal dependency of the application layer, which is an entry of that pull request. So the subscription state machine, the SSE route, the WebSocket session and route, supervision and shutdown, which all reach `parse_event` or `TailEvents`, follow story 3.2. Everything that does not reach it (scaffold, configuration, origins, broker, domain, window, status, hub, frames, status route) comes before it.
>
> Assumption: the frame encoder of story 2.3 writes the WebSocket `type` member and the `error` member as `"` + text + `"` without calling `serde_json`. An event type name only holds `a-z 0-9 . _ -` and every error reason of the protocol is a fixed ASCII text without `"`, `\` or a control character, so the output is byte-equal to `serde_json::to_string` (tested against it as a dev-dependency, which the application layer already allows). This keeps the hub and the frames free of the protected entry; `architecture.md`'s `http/frame.rs` signatures are unchanged.
>
> Assumption: the proof stories (Epic 4) come before the removal (Epic 5), not after it as the task text ordered. FR-34 makes the removal "the last epic", and the notification feature must not wait for the second label `approved-breaking-change` (decision D10). The full verification of the change (Epic 6) runs after the removal.
>
> Assumption: the Kafka broker in the compose environments and CI (story 1.3) needs no approval, because `architecture.md` keeps it out of every protected file (`DEPS` and the Bats files untouched, the host listener in a compose file `make start` does not read). It is therefore placed before the approval.
