# Epics and Stories: real-time event delivery hub (issue #4)

This file slices the revised design of `architecture.md` of this bundle into stories for the contexts `notification/event-stream` and `internal/cluster`. It adds no component: every file, type, constant, limit, query number (Q1 to Q13), route, variable and message text named below is the one of `architecture.md` and `prd.md` after the validation (the section "Revisions after validation" of `architecture.md` lists what changed). Where a story names a test list of `architecture.md`, that list is binding for the story. A decision taken while slicing is a line `> Assumption:` in the story it affects.

**How the stories run:**

- The stories run in waves. A story is ready when the stories of its `Depends on:` line are done, and the ready stories form one wave. One implementer works on each story, all stories of a wave in parallel in one working tree. One serialized verify step then runs the DB-backed targets on the tree, and each story is committed on its own through the hooks, which check the tree that is already green.
- (i) Only the tree at the end of a wave has to compile and pass the lint and unused-dependency gates. A story alone does not have to: while its wave runs, a compile error or a finding in a file of another story of the wave is not its failure.
- (ii) `Cargo.lock` is regenerated by cargo and may change in several stories of a wave. No story edits it by hand.
- (iii) Two stories of a wave may each add their own lines to the same manifest, `lib.rs`, `http.rs`, `tests/integration/main.rs`, `tests/support/src/lib.rs`, `.templatesyncignore`, `.env` or `docs/environment.md`. They never rewrite the same function, struct, test or section. Every such line has one writer, named in a "Scope" list; a story that needs a line of another story of its wave says so and does not write it a second time.
- (iv) A story uses only types that exist before its wave starts. Every type it names comes from a story of an earlier wave, and a `Depends on:` edge orders the two. An edge that only places a story in its wave, with no type behind it, is called an "order" edge in the story text.
- (v) A story that adds or changes a `sqlx::query!` macro owns the database in its wave (1.1, 1.2 and 3.6). `SQLX_OFFLINE=true` (the protected `.cargo/config.toml`) turns a query without metadata into a compile error of the whole workspace. So from the moment such a story has written a query, it runs `make.sqlx_prepare` itself, right after each adapter and again after every change of a query text, before any other target that compiles the workspace, `make.migrate` and `make.migrate_rollback` included. `make.sqlx_prepare` resets and migrates the test database from the migration files and rebuilds the files of `.sqlx/` from a build of all targets, so it needs the migration pair and no earlier `make.migrate`. The files of `.sqlx/` are committed with the query. Stories 1.1 and 1.2 run alone. Story 3.6 shares its wave only with story 4.1, which touches no SQL; until story 3.6 has written its `.sqlx/` files, a workspace-wide target of story 4.1 can fail to compile in the infrastructure crate, which rule (i) covers. `make.sqlx_prepare` builds every target of the workspace, so it also fails on a compile error in a file of story 4.1: the session of story 3.6 then runs the target again and changes no file of story 4.1, and the session of story 4.1 leaves `http/hub.rs` and its tests compiling whenever it stops editing (the output of `make.lint_code` names the crate of each error). To keep that window short, the orchestrator starts story 4.1 only after the implement step of story 3.6 has ended. In this wave story 3.6 is the one session that runs DB-backed targets and story 4.1 runs only the DB-free ones, which is the serialized use of the database that part (b) of the constraints asks for.
- Every wave ends green on the whole gate set that the verify step runs: `make.format`, `make.lint_code`, `make.static_analysis`, `make.unit_tests`, `make.architecture`, `make.complexity`, `make.check_crate_isolation`, `make.unused_dependencies`, `make.check_security`, `make.validate_architecture_model`, `make.setup_test_db`, `make.sqlx_prepare`, `make.validate_sqlx_metadata`, `make.integration_tests`, `make.tests_with_coverage`, `make.e2e_tests`, `make.validate_contract_snapshots`, `make.docs_check` and, after the story commits, `make.mutation_tests_diff` with `base_ref=<commit before the wave>`. The last criterion of a story names only the gates that prove that story.
- The mutation run of a wave is never vacuous. It runs after the commits of the wave, so that new files are tracked and the protected `scripts/mutation-diff.sh` sees them. A wave that added or changed production Rust and whose run names no mutant is not recorded as passed. A wave without production Rust (waves 9 to 11) records "no mutants" with that reason. A surviving or timed-out mutant is fixed by a further commit in the files of the owning story before the next wave starts.
- Every story carries its own tests to the bar of the repository: 100 % line and function coverage of its code, both sides of every boundary, every error branch and every log entry asserted, every awaited call of a test inside `tokio::time::timeout`, paused tokio time wherever a timer is involved. No story plans an `allow` attribute, a coverage or mutation exclusion, a protected-file edit or a lowered bar. The only lint expectations are the ones `architecture.md` names, in the form the repository already uses: the item-level `#[expect(clippy::disallowed_methods, reason = "..")]` on a test helper that opens a socket (stories 4.4, 5.2, 6.2 and 6.4) and the `unused_async` expectation of a handler that awaits nothing (story 1.2).
- The test doubles of `tests/support` are complete in the story that creates them (1.1, 1.2 and 3.1): every control a later story needs is there (failing, hanging, a gate, call budgets, scripted results, recorded calls), so no later story edits `tests/support`. A double records a port call before it checks its failure, hang or gate mode, so a failed or pending call is counted. A record holds no time. A mode is switched at run time through the shared handle of the double.
- A test that subscribes first makes the hub ready, because the hub answers 503 until the relay has its start cursor: `EventPublisher::started(&*hub, cursor)` in the unit tests of the application crate, one successful `relay.tick()` right after an `Application` is built in the in-process tests of `crates/service` and in the Gherkin world, and a repeated request while the answer is the 503 problem `the node is starting` in a test of the served binary.
- A dependency enters a member manifest in the story whose code first uses it, and a crate-private item is added by the story of its first caller: the unused-dependency gate and the lint gate refuse the one and the other without a use.
- Story ids against the first draft of this file: 3.4 was 3.5 (ingest), 3.5 was 5.1 (SQS adapter), 3.6 was 3.4 (PostgreSQL log), 5.1 was 5.2 (loops), 5.2 was 5.3 (wiring). The other ids are unchanged.

## Epic 4: Subscriptions and streaming transports

The epic delivers events to clients: the in-process hub with bounded queues, the subscription that reads the log by position and uses the queue of the hub as its fast path, the SSE route and the WebSocket route with run-time commands. A subscriber whose queue is full is not disconnected: it falls behind and catches up from the log on its connection. After the epic the application crate serves both routes; events still enter only through tests until Epic 5 schedules the loops.
