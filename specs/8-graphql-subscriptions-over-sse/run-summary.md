## Assumptions

Every `> Assumption:` line of the other files of the bundle, in file order (`implementation-readiness.md` holds none). An assumption added by the correct-course round of 2026-11-21 is appended to its file's list with its place, so the numbers that earlier rounds cite stay valid.

### research.md (35)

1. only the distinct connections mode of graphql-sse is implemented; the single connection mode is not, because its reservation must stay on one node across the PUT, the stream, the POSTs and the DELETE, which needs sticky sessions or shared state that ADR 0014 excludes, and the protocol's own recipes say the distinct mode suffices for most uses.
2. the endpoint is the GraphQL endpoint `/api/graphql` itself, chosen by content negotiation and not by a sibling path, because the issue's criteria send the subscription and the query "to the GraphQL endpoint with `Accept: text/event-stream`", and graphql-sse clients and Yoga use one URL for both transports.
3. a request is answered as an event stream when its `Accept` header lists `text/event-stream` with a q value above 0 and above that of every `application/graphql-response+json` and `application/json` range it lists; every other POST (no header, `*/*`, `text/*`, a JSON type first or equal) keeps the JSON transport, whose answers are unchanged apart from the length bounds of decision M5 (amended on 2026-11-21). This streams the graphql-sse client (exactly `text/event-stream`), `EventSource` and urql's subscriptions, and keeps urql's queries, which list JSON types with the same q, on JSON. A GET, which has no JSON representation, follows the GET rule of the assumption on Schemathesis below (amended on 2026-11-17).
4. `GET /api/graphql` that negotiates SSE is served with the parameters `query`, `operationName`, `variables` and `extensions` (the last two JSON-encoded), as GraphQL over HTTP section 4.3 describes, so that a browser `EventSource` can subscribe and resume natively; a `GET` that does not negotiate SSE keeps today's status and body (the explorer in `dev`, otherwise the 405 problem with `Allow: POST`); its answers gain only `vary: accept`, and the 405 of other methods lists `GET, HEAD, POST`, so the existing router test and feature stay valid. JSON queries over GET are not added.
5. the subscription field is `events(types: [String!]!, lastEventId: String): Event!`, and `Event` has `id: String!` (the event id as a decimal string, because ids exceed both GraphQL `Int` and the integers a JavaScript number holds exactly), `type: String!` and `data: JSON!` (the event object, i.e. the envelope). This mirrors the WebSocket frame `{"id","type","data"}`. No description holds a word that the schema test refuses.
6. the `Last-Event-ID` header wins over the `lastEventId` argument, as on the REST streaming routes (bundle 4 FR-12): an `EventSource` reconnects with its original URL plus a newer header, and the graphql-sse client re-sends its first body, to which an application adds the header through the client's `headers` function.
7. invalid arguments are answered with `200 text/event-stream`, one `next` event whose data is `{"data":null,"errors":[...]}` with `extensions.code` `VALIDATION_FAILED`, then `complete`, then the end, and no hub subscriber is registered. The `types` rules and codes are those of the REST routes (`required`, `length`, `pattern`, `max_items`, property `types`). A malformed cursor gives one violation whose property is the carrier read (`Last-Event-ID` or `lastEventId`), whose message is the REST text "<carrier> must be a decimal unsigned 64-bit integer", and whose code is `format`. The protocol requires this: validation found before execution MUST travel through an accepted SSE connection. "No stream of events is opened" therefore means that no hub subscription and no event exist. The resolver builds a 422 problem and converts it with `problem_to_error`, so the shared helper stays unchanged.
8. a node that is starting, at its subscriber capacity or shutting down answers the subscription before any SSE head with the same 503 problem as the REST streaming routes (`detail` the hub's text, the `subscription rejected` log). Availability is not a validation step of the operation, and GraphQL over HTTP section 5.4 names 503 for load shedding. The graphql-sse client retries any non-2xx answer with backoff, possibly on another node, and the existing documentation already says a 503 is safe to retry on any node. No hub slot is taken.
9. the handler drives the operation before it writes the head until one of three things happens: the resolver reports that the subscription opened, the resolver reports a refusal, or the first result arrives. This runs under `HTTP_REQUEST_TIMEOUT`. A query is therefore executed within the request budget, a refusal can still become a 503, and no answer waits for a broker read, because opening a subscription reads no broker.
10. a subscription operation must select exactly one root field, and that field must not be an introspection field, as the GraphQL specification rule 5.2.3.1 requires; the service enforces it as the direct-field rule (exactly one field selection written directly at the root, no root fragment), because async-graphql makes one stream per direct root field and skips root fragments. The rule is checked before any resolver runs. A violation is answered like an invalid argument: one `next` with `VALIDATION_FAILED`, then `complete`, and no hub subscriber. async-graphql does not enforce the rule.
11. the GraphQL stream is written as bytes, not through `axum::response::sse`, because axum cannot write the bare `data:` line of `complete`. Its events are: a subscription result: `event: next`, `id: <event id>`, `data: <result>`; a query or error result: `event: next`, `data: <result>`; the end: `event: complete` and a bare `data:`; a keep-alive: the comment `:`; Each event ends with an empty line. The JSON is always compact, on one line.
12. the head is `200` with `content-type: text/event-stream`, `cache-control: no-cache` and `x-accel-buffering: no`, as on the existing SSE route. It has no `connection` header, which HTTP/2 forbids, and no `content-encoding: none`, which is not a registered content coding (the router has no compression layer).
13. the stream writes one comment right after the head, following the reference handler, so that browsers whose fetch waits for the first body bytes see the response at once. After that it writes a comment whenever `STREAM_KEEP_ALIVE` passes with nothing written, which meets the issue's keep-alive criterion.
14. a subscription stream that ends because the hub closed (shutdown, or the tail stopped) or because a replay failed ends without `complete`, so the client reconnects with its last id on any node; a failed replay writes `replay failed` with its own transport label. `complete` is written only after a single-result operation or an error result.
15. a query sent with `Accept: text/event-stream` answers one `next` with its result, then `complete`. A mutation cannot run, because the schema has no mutation root, so a mutation over GET cannot change state, and the reference's 405 for mutations over GET is not reproduced. A subscription sent without SSE negotiation keeps today's JSON answer ("Subscriptions are not supported on this transport.").
16. a request that is not a GraphQL request is refused before any stream, whatever it negotiates. On POST that is a body without a string `query`, answered with the 422 problem of today. On GET it is an unreadable or repeated parameter, answered 400 as on the SSE route, or `variables` or `extensions` that are not JSON objects, answered 422. Parse and validation errors of a GraphQL document go through the stream, as the protocol requires.
17. the transport learns the id of each subscription result from per-request data that the resolver fills before it yields the result, and not from the client's selection set, which may omit or alias `id`.
18. GraphQL resolution and serialisation of each event run in the subscriber's connection task. The hub keeps encoding one shared frame per event, and the publish path never waits for a GraphQL client (bundle 4 NFR-2, NFR-10). How the event object is taken from the frame (parsed per subscriber, or shared once parsed) is left to the architecture.
19. the code is placed like this: the resolver goes in the event-stream application crate's `graphql` module, the only module there that may import `async_graphql` besides `http`, so it reaches `parse_names` and `Subscriptions::open` crate-internally; the schema root and the GraphQL over SSE transport go in the composition root, which owns the schema and its transports (AD-18); the handler that reads `Accept` and `Last-Event-ID` takes `HeaderMap`, the recorded streaming exception, and the composition root's extractor oracle is extended with it.

Credentials are not offered, because there is no subscriber authorization. Tests prove both cases for the POST and the `EventSource` form.
