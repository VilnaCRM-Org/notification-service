## Assumptions

Every `> Assumption:` line of the other files of the bundle, in file order (`implementation-readiness.md` holds none).

### research.md (31)

1. only the distinct connections mode of graphql-sse is implemented; the single connection mode is not, because its reservation must stay on one node across the PUT, the stream, the POSTs and the DELETE, which needs sticky sessions or shared state that ADR 0014 excludes, and the protocol's own recipes say the distinct mode suffices for most uses.
2. the endpoint is the GraphQL endpoint `/api/graphql` itself, chosen by content negotiation and not by a sibling path, because the issue's criteria send the subscription and the query "to the GraphQL endpoint with `Accept: text/event-stream`", and graphql-sse clients and Yoga use one URL for both transports.
3. a request is answered as an event stream when its `Accept` header lists `text/event-stream` with a q value above 0 and above that of every `application/graphql-response+json` and `application/json` range it lists; every other POST (no header, `*/*`, `text/*`, a JSON type first or equal) keeps the JSON transport unchanged. This streams the graphql-sse client (exactly `text/event-stream`), `EventSource` and urql's subscriptions, and keeps urql's queries, which list JSON types with the same q, on JSON. A GET, which has no JSON representation, follows the GET rule of the assumption on Schemathesis below (amended on 2026-11-17).
4. `GET /api/graphql` that negotiates SSE is served with the parameters `query`, `operationName`, `variables` and `extensions` (the last two JSON-encoded), as GraphQL over HTTP section 4.3 describes, so that a browser `EventSource` can subscribe and resume natively; a `GET` that does not negotiate SSE keeps today's status and body (the explorer in `dev`, otherwise the 405 problem with `Allow: POST`); its answers gain only `vary: accept`, and the 405 of other methods lists `GET, HEAD, POST`, so the existing router test and feature stay valid. JSON queries over GET are not added.
5. the subscription field is `events(types: [String!]!, lastEventId: String): Event!`, and `Event` has `id: String!` (the event id as a decimal string, because ids exceed both GraphQL `Int` and the integers a JavaScript number holds exactly), `type: String!` and `data: JSON!` (the event object, i.e. the envelope). This mirrors the WebSocket frame `{"id","type","data"}`. No description holds a word that the schema test refuses.
6. the `Last-Event-ID` header wins over the `lastEventId` argument, as on the REST streaming routes (bundle 4 FR-12): an `EventSource` reconnects with its original URL plus a newer header, and the graphql-sse client re-sends its first body, to which an application adds the header through the client's `headers` function.
7. invalid arguments are answered with `200 text/event-stream`, one `next` event whose data is `{"data":null,"errors":[...]}` with `extensions.code` `VALIDATION_FAILED`, then `complete`, then the end, and no hub subscriber is registered. The `types` rules and codes are those of the REST routes (`required`, `length`, `pattern`, `max_items`, property `types`). A malformed cursor gives one violation whose property is the carrier read (`Last-Event-ID` or `lastEventId`), whose message is the REST text "<carrier> must be a decimal unsigned 64-bit integer", and whose code is `format`. The protocol requires this: validation found before execution MUST travel through an accepted SSE connection. "No stream of events is opened" therefore means that no hub subscription and no event exist. The resolver builds a 422 problem and converts it with `problem_to_error`, so the shared helper stays unchanged.
8. a node that is starting, at its subscriber capacity or shutting down answers the subscription before any SSE head with the same 503 problem as the REST streaming routes (`detail` the hub's text, the `subscription rejected` log). Availability is not a validation step of the operation, and GraphQL over HTTP section 5.4 names 503 for load shedding. The graphql-sse client retries any non-2xx answer with backoff, possibly on another node, and the existing documentation already says a 503 is safe to retry on any node. No hub slot is taken.
9. the handler drives the operation before it writes the head until one of three things happens: the resolver reports that the subscription opened, the resolver reports a refusal, or the first result arrives. This runs under `HTTP_REQUEST_TIMEOUT`. A query is therefore executed within the request budget, a refusal can still become a 503, and no answer waits for a broker read, because opening a subscription reads no broker.
10. a subscription operation must select exactly one root field, and that field must not be an introspection field, as the GraphQL specification rule 5.2.3.1 requires; the service enforces it as the direct-field rule (exactly one field selection written directly at the root, no root fragment), because async-graphql makes one stream per direct root field and skips root fragments. The rule is checked before any resolver runs. A violation is answered like an invalid argument: one `next` with `VALIDATION_FAILED`, then `complete`, and no hub subscriber. async-graphql does not enforce the rule.
11. the GraphQL stream is written as bytes, not through `axum::response::sse`, because axum cannot write the bare `data:` line of `complete`. Its events are: a subscription result: `event: next`, `id: <event id>`, `data: <result>`; a query or error result: `event: next`, `data: <result>`; the end: `event: complete` and a bare `data:`; a keep-alive: the comment `:`; Each event ends with an empty line. The JSON is always compact, on one line.
12. the head is `200` with `content-type: text/event-stream`, `cache-control: no-cache` and `x-accel-buffering: no`, as on the existing SSE route. It has no `connection` header, which HTTP/2 forbids, and no `content-encoding: none`, which is not a registered content coding (the router has no compression layer).
13. the stream writes one comment right after the head, following the reference handler, so that browsers whose fetch waits for the first body bytes see the response at once. After that it writes a comment whenever `STREAM_KEEP_ALIVE` passes with nothing written, which meets the issue's keep-alive criterion.
14. a subscription stream that ends because the hub closed (shutdown, or the tail stopped) or because a replay failed ends without `complete`, so the client reconnects with its last id on any node; a failed replay writes `replay failed` with its own transport label. `complete` is written only after a single-result operation or an error result.
15. a query sent with `Accept: text/event-stream` answers one `next` with its result, then `complete`. A mutation cannot run, because the schema has no mutation root, so a mutation over GET cannot change state, and the reference's 405 for mutations over GET is not reproduced. A subscription sent without SSE negotiation keeps today's JSON answer ("Subscriptions are not supported on this transport.").
16. a request that is not a GraphQL request is refused before any stream, whatever it negotiates. On POST that is a body without a string `query`, answered with the 422 problem of today. On GET it is an unreadable or repeated parameter, answered 400 as on the SSE route, or `variables` or `extensions` that are not JSON objects, answered 422. Parse and validation errors of a GraphQL document go through the stream, as the protocol requires.
17. the transport learns the id of each subscription result from per-request data that the resolver fills before it yields the result, and not from the client's selection set, which may omit or alias `id`.
18. GraphQL resolution and serialisation of each event run in the subscriber's connection task. The hub keeps encoding one shared frame per event, and the publish path never waits for a GraphQL client (bundle 4 NFR-2, NFR-10). How the event object is taken from the frame (parsed per subscriber, or shared once parsed) is left to the architecture.
19. the code is placed like this: the resolver goes in the event-stream application crate's `graphql` module, the only module there that may import `async_graphql` besides `http`, so it reaches `parse_names` and `Subscriptions::open` crate-internally; the schema root and the GraphQL over SSE transport go in the composition root, which owns the schema and its transports (AD-18); the handler that reads `Accept` and `Last-Event-ID` takes `HeaderMap`, the recorded streaming exception, and the composition root's extractor oracle is extended with it.
20. CORS needs no code change: the allow-list of `CORS_ALLOWED_ORIGINS` already allows `GET`, `POST`, `content-type` and `last-event-id`; without the variable the router has no CORS layer, so no other origin can read the stream. Credentials are not offered, because there is no subscriber authorization. Tests prove both cases for the POST and the `EventSource` form.
21. ADR 0021 "GraphQL subscriptions over Server-Sent Events" records the protocol choices and amends the "with no subscription" sentence of ADR 0007. The ADR index marks the amendment, as it marks 0005 superseded by 0020. Template ADR 0007 is not rewritten.
22. `.templatesyncignore` gains `crates/service/src/graphql/handler.rs`, plus `crates/service/src/graphql.rs` if that file is edited. `crates/shared/application/src/graphql.rs` stays unchanged and needs no entry.
23. the K6 subscriptions scenario gains held GraphQL SSE subscribers (POST with `Accept: text/event-stream`) within the existing `subscriptions` budgets, which are not protected. This shows that the new transport holds under the smoke profile that `make ci` runs.
24. the development explorer stays unchanged. Its fetcher has no SSE support, and running subscriptions from it is not a criterion. The documentation says subscriptions are run with a graphql-sse client, urql or `EventSource`.
25. the HTTP/1.1 limit of 6 connections per origin is documented together with the recommendation to serve HTTP/2 at the edge. It is accepted rather than addressed through the single connection mode.
26. every route the service serves, the documentation routes and `/ping` included, becomes an operation of the OpenAPI document (eleven operations), because the maintainer's decision of 2026-11-17 asks for every endpoint and for a test that fails on any route served without an entry.
27. every route is registered through `OpenApiRouter::routes(routes!(..))`, so the router and the document come from the same annotation, and a source oracle fails on any `.route(`, `.route_service(` or `.nest_service(` call; the composition root merges three routers (REST with `AppState`, GraphQL with `ApiSchema`, operational without state) into one router and one document.
28. the documentation asset route becomes `/api/docs/{file}`, one segment, because utoipa-axum writes the annotated path verbatim into the document and `{*file}` is not an OpenAPI path template; the embedded Swagger UI files are one segment deep [I], and the story proves that every asset the page loads is served.
29. a GET of `/api/graphql` whose `Accept` admits the event stream through a wildcard negotiates SSE, and a GET without `Accept` keeps today's answer; this fixes at its root the only Schemathesis conflict found (its `Accept: */*`), keeps every existing test that sends no `Accept`, and follows RFC 9110 12.5.1 for the wildcard and the "Accept" section of GraphQL over HTTP, which lets a server answer a request without `Accept` as it chooses (`prd.md` FR-2).
30. no exclusion from Schemathesis is planned. A failure on a streaming operation is fixed in the document or the code; one that cannot be fixed at its root stops the story and goes to the maintainer with the exact exclusion, which the plan never makes itself.
31. ADR 0022 "Every route in the OpenAPI document" records these decisions and amends ADR 0006 and ADR 0007; `API_VERSION` becomes 2.1.0.

### prd.md (42)

1. the field is `events(types: [String!]!, lastEventId: String): Event!` and the object is `Event { id, type, data }`, because that is the frame of the WebSocket route (4/FR-9) that the issue names "the event object (id, type and the envelope data)"; one shape on every transport lets a client share its parser. The sorted SDL prints the arguments in the order `lastEventId`, `types`; the order is not part of the API.
2. `Event.id` is a `String!` holding the decimal id, not an `Int` or `ID`, because event ids are 64-bit and exceed GraphQL `Int` and the integers a JavaScript number holds exactly; the status object already writes its 64-bit values as decimal strings.
3. `Event.data` is one `JSON!` scalar rather than a typed envelope object, because the producer's `data` member is any JSON value and needs a JSON scalar anyway, and a single scalar keeps the value identical to the SSE and WebSocket forms. A typed envelope is a possible later addition and would not break this field.
4. `Event.data` costs 501 so that one execution result holds at most one copy of the event object. Every other selected field costs 1, and FR-10 allows aliases and fragments, so without this cost a document such as `{ events(..) { d1: data d2: data ... d999: data } }` passes the limit of 1 000. async-graphql resolves `Json<T>` with one `to_value` per selection, so such a document would build 999 copies of every event of its type, per subscriber, in the node's shared memory: about 64 MiB per event with the default `EVENT_MAX_DATA_BYTES`, about 1 GiB at its maximum. A cost above half the limit refuses every document that selects `data` twice, keeps `{ id type data }` valid, and needs neither a new variable nor a new rule of the service. Repeating `id` or `type` costs at most 1 000 short strings per event and stays bounded.
5. the subscription root has one field. Narrower subscriptions (by project, by envelope member) are out of scope as in bundle 4.
6. a GET whose `Accept` admits the event stream only through a wildcard (`*/*`, `text/*`) negotiates SSE, unlike a POST. RFC 9110 12.5.1 lets a wildcard accept every type, and outside the explorer the event stream is the only representation a GET of `/api/graphql` has, so serving it is proactive negotiation and not a guess. It is also the root-cause fix for Schemathesis (FR-29): Schemathesis sends `Accept: */*`, and a 405 to a schema-valid GET would fail its check `positive_data_acceptance`. A GET without any `Accept` field keeps today's 405 (or the explorer in `dev`): GraphQL over HTTP (section "Accept") lets a server answer a request without `Accept` with an error or any media type, a client that wants a stream says so, and keeping the answer leaves every caller of today unchanged; the router test `the_explorer_exists_only_in_dev` and `features/graphql.feature` send no `Accept` and stay unchanged. A browser navigation ranks `text/html` above its `*/*;q=0.8`, so it keeps the explorer in `dev` and the 405 elsewhere. In `dev`, curl with its default `*/*` now gets an event stream (the 400 problem of a missing `query` when it sends none) instead of the explorer; the documents say so.
7. the endpoint is `/api/graphql` itself and not a sibling path, because the issue sends both the subscription and the query "to the GraphQL endpoint with `Accept: text/event-stream`", and the graphql-sse client, urql and GraphQL Yoga use one URL for both transports.
8. `Accept` is parsed as media ranges with q values and is not compared as one string. The reference handler streams only on an exact `text/event-stream`, which would break urql's subscriptions (`text/event-stream, multipart/mixed`). A "contains" test would stream urql's queries, which list `text/event-stream` with the same q as the JSON types. GraphQL over HTTP 4.2 asks the server to use the highest-priority type it supports. A tie goes to JSON because JSON is today's default and urql's queries rely on it. On POST, wildcards do not choose the event stream, so no existing POST client changes transport; the GET rule, where JSON is not a representation, follows below.
9. only the distinct connections mode of graphql-sse is served. Its single connection mode keeps a reservation in the memory of one node across a PUT, the stream, every POST and a DELETE. That needs sticky sessions or shared state, which ADR 0013 and ADR 0014 exclude. The protocol's recipes say the distinct mode suffices for most uses.
10. the POST form is the GraphQL over HTTP request that the specification requires every server to support (4.4). The graphql-sse client always sends it, with `content-type: application/json` and exactly `accept: text/event-stream`.
11. the GET form exists for the browser `EventSource`, which can only send GET and cannot set headers. Its parameters are those of GraphQL over HTTP 4.3, and the graphql-sse recipes put `query` in the URL the same way. It is served in every `APP_ENV`, because `EventSource` pages run in production.
12. the query string is bounded by `HTTP_MAX_BODY_BYTES` and answered 414 beyond it, so that a document has the same byte budget in both forms and no new variable is needed. GraphQL over HTTP 5.4 names 414 for this case. Without the bound, only the HTTP server's header buffer, about 400 KiB, would limit it.
13. `variables` and `extensions` that are not JSON objects are answered with the 422 violation of the codebase's query-parameter convention: a parameter that is read but breaks a constraint is a 422 with a violation, and a parameter that cannot be read is a 400. GraphQL over HTTP's 405 for a mutation over GET is not reproduced, because no mutation can exist in this schema.
14. a GET without SSE outside `dev` keeps the 405 problem with `Allow: POST`. GraphQL over HTTP uses this answer for a GET that the server will not run although it serves GET otherwise (a mutation over GET): POST is the method that answers a request for JSON. The existing router test and `features/graphql.feature` stay valid. JSON queries over GET are not added.
15. the 405 answer to a GET that does not negotiate SSE keeps `Allow: POST` although GET serves event streams. This deliberately deviates from RFC 9110 §15.5.6, which asks a 405 to list every method the resource supports, to keep today's answer (router test `the_explorer_exists_only_in_dev`, `features/graphql.feature`); `docs/streaming-protocol.md` documents the event-stream form of GET.
16. the `Allow` header of the other methods lists `GET, HEAD, POST`, so that the methods the router serves are listed: axum writes it from the registered methods, and GET now serves event streams in every environment. It is the one header of a non-SSE answer whose value changes. `features/http_errors.feature` ("allow should contain POST") still holds.
17. `Vary: Accept` is added to every answer of GET `/api/graphql`, because the representation now depends on `Accept` (RFC 9110 12.5.5). Without it a shared cache could hand the stored 405 or explorer page to an `EventSource` request for the same URL. POST answers are not reused by caches without explicit freshness, which the service never sends, so the JSON transport stays unchanged. The brief's S8 states the same: same status and body; only `Vary` on GET answers and `Allow` on other methods change.
18. the head mirrors the SSE route, `content-type: text/event-stream`, `cache-control: no-cache` and `x-accel-buffering: no`, so proxies treat both streams alike. The SSE format is always UTF-8 (WHATWG), so the reference's `charset=utf-8` adds nothing. A `connection` header is forbidden in HTTP/2. `content-encoding: none` is not a registered coding, and the router has no compression layer.
19. `next` and `complete` are the only events of the graphql-sse protocol. Its client treats any other event name as fatal ("Invalid stream event"), so the GraphQL stream never reuses the event-type names of the SSE route.
20. `complete` carries a bare `data:` line, as the protocol requires. An `EventSource` does not dispatch an event whose data buffer is empty, and a `data:` line adds a line feed to that buffer. urql does not read a `data:` line without a value as a result, which it would do with `data: null`. Because axum's `Event::data("")` writes no `data:` line, the stream is written as bytes and not through `axum::response::sse`.
21. the `id:` line appears on subscription results only. A browser `EventSource` stores it and sends it back as `Last-Event-ID` when it reconnects, while the graphql-sse and urql parsers ignore it harmlessly. A single result carries none, so a query or an error result never changes a client's last event id.
22. no `retry:` field is written. The graphql-sse client ignores it and has its own randomised backoff. For `EventSource`, a fixed server delay would bring the clients of a node back together without the random part of the documented reconnect procedure. The SSE route writes none either.
23. async-graphql runs a subscription lazily, so a refusal or an argument error shows only when the operation is first driven. Driving the operation to one of the three points before the head is the only way to answer a refusal with a 503 and to keep a query inside the request budget, which bounds only the time to the response head. "Pending at the first poll" is not a usable signal, because a subscription yields cooperatively on idle steps.
24. the transport learns the id of each result from per-request data that the resolver fills before it yields the result, and not from the client's selection set, which may omit or alias `id`.
25. the `Last-Event-ID` header wins over the `lastEventId` argument, as on the REST streaming routes (4/FR-12). An `EventSource` reconnects with its original URL, whose document may still hold an old argument, plus a newer header. The graphql-sse client re-sends its first body on a retry, and the application adds the header through the client's `headers` function, which the client evaluates on every attempt.
26. invalid arguments are answered inside an accepted event stream, because the graphql-sse protocol requires validation that runs before execution to report through an accepted SSE connection: a 4xx makes an `EventSource` fail without telling the page why, and makes the graphql-sse client retry a request that cannot succeed. "No stream of events is opened" (AC4) therefore means that no hub subscriber and no event exist; the stream carries only the error result.
27. the type rules, codes and messages are those of the REST routes, so a client meets one rule. A malformed cursor, a 400 on the REST routes, becomes a violation with the code `format` on the carrier that was read, so that it gets `VALIDATION_FAILED` as AC4 asks. The resolver builds a 422 problem and converts it with `problem_to_error`, so the shared helper stays unchanged.
28. the rule is enforced by the service, because async-graphql has no single-root-field validation rule. Without it, `subscription { a: events(..) b: events(..) }` would register two hub subscribers for one request and interleave two id sequences on one stream.
29. the rule is the direct-field rule and not the wording of GraphQL specification 5.2.3.1 (one response name after fragments are expanded), because async-graphql 7.2.1's `collect_subscription_streams` makes one stream per direct `Selection::Field` of the root and skips root fragments (`async-graphql-7.2.1/src/subscription.rs:43-44`). Under the specification's wording, `subscription { ...F }` would pass and run nothing, a 200 stream that opens no subscriber and writes only `:` and `complete`, and `events(..) { id } events(..) { type }` would register two hub subscribers. The direct-field rule refuses more documents than the specification and never runs more or fewer than one subscriber. The ban on `@skip` and `@include` at the root keeps "one request, one subscriber" independent of variables, as the current GraphQL specification draft and graphql-js do.
30. document errors travel through the accepted stream for the reason of FR-13, which is the protocol's rule. They keep the messages of the JSON transport and gain no code, so the GraphQL error model stays one model; the stable codes of AD-18 belong to resolver errors.
31. availability is answered before the stream, with the 503 problem the REST streaming routes answer, and not as an error result inside the stream. Availability is not a validation step of the operation, and GraphQL over HTTP 5.4 names 503 for load shedding. The graphql-sse client retries any non-2xx answer with randomised backoff, possibly on another node, while an error result followed by `complete` would end its subscription for good. `docs/streaming-protocol.md` already says a 503 is safe to retry on any node. An `EventSource` does not retry a 503 by itself; the page creates a new one, as for the SSE route.
32. the first comment follows the reference handler. Some browsers (Firefox, Safari) show a fetched response only after its first body bytes, not after the head. The interval is `STREAM_KEEP_ALIVE` and not the reference's 12 s, so that every stream of the service follows one setting, which is also the socket send bound; WHATWG suggests about 15 s for legacy proxies.
33. a subscription that is cut ends without `complete`, so that clients resume. The graphql-sse client retries a connection that closed while results were expected ("Connection closed while having active streams") and does not reconnect after `complete`. An `EventSource` reconnects with `Last-Event-ID` unless the page closed it, and the page closes it when it sees `complete`. `complete` is therefore written only when the operation has really finished.
34. queries are accepted over SSE because AC7 asks for it and the reference handler does the same: one result becomes one `next`, then `complete`. Running the query before the head keeps it inside the request budget.
35. CORS needs no code change. The allow-list already allows `GET`, `POST`, `content-type` and `last-event-id`. The `Accept` values of the reference clients are CORS-safelisted (at most 128 bytes, no unsafe byte). Without the variable the router has no CORS layer at all. Credentials are not offered, because there is no subscriber authorization; the graphql-sse client's default `credentials: 'same-origin'` and an `EventSource` without `withCredentials` both work.
36. the GraphQL subscribers are added within the existing budgets, which are not protected files. They show that the new transport holds under the smoke profile that `make ci` runs, and no capacity figure is claimed.
37. ADR 0021 amends ADR 0007 instead of rewriting it, because ADR 0007 is a template record and the index already shows how a later record changes an earlier one. ADR 0022 amends ADR 0006 and ADR 0007 the same way.
38. "every route the service serves" includes the three documentation routes and `/ping`, besides the routes the issue names "at least", because the issue asks that a test fail for any route served without an entry; a route left out would need its own exception in that test.
39. the documentation asset route is served and documented as `/api/docs/{file}`, one path segment, instead of today's catch-all `/api/docs/{*file}`. utoipa-axum registers the annotated path verbatim in both the router and the document, and `{*file}` is not an OpenAPI path template; the embedded Swagger UI files are one segment deep, so every asset the page loads is still served, and a deeper path gets the router's 404 problem instead of the handler's 404 problem.
40. the WebSocket handshake headers are documented as required header parameters with the values the upgrade accepts (`Connection` holding `Upgrade`, `Upgrade: websocket`, `Sec-WebSocket-Version: 13`, a `Sec-WebSocket-Key`), because they are what a client must send; without them the route answers the 400 or 426 problem of the upgrade, which is documented too. OpenAPI 3.1 has no WebSocket object, so the frames of both directions are described in the 101 response and its examples.
41. the GraphQL operations get the tag `GraphQL`, and the three documentation routes the tag `Documentation`; `/ping` joins `HealthCheck`, next to `/api/health`.
42. no exclusion is planned, because Schemathesis 4.33.1 can test every operation of FR-26 (`research.md` section 3.11): it reads an event stream until the stream ends, 20 events arrive or its 10 s request timeout passes, and treats a stream cut short as a normal response; it validates each event against a `text/event-stream` schema of one event; it sends `Accept: */*`, which the GET rule of FR-2 answers with an event stream instead of the 405 that its check `positive_data_acceptance` would refuse; and it accepts a documented 101. The escalation path is the issue's own rule for a failure that cannot be fixed at its root.

### architecture.md (21)

1. the resolver and its objects live in the event-stream application crate's `graphql` module, and the transport lives in the composition root. AD-18 puts the schema and its transports in the composition root. The crate's module rule lets only `http` and `graphql` import `async_graphql`, and the resolver reaches `parse_names`, `types_problem`, the cursor rule and `Subscriptions::open` crate-internally, as `EventStreamQuery` reaches `list_types`. The transport never names a type of the hub other than `HubError` and `Sequence`.
2. the new transport modules of the composition root are private modules with `pub(crate)` items. Only `handler.rs` holds `pub async fn` handlers, so the handler-source list of the router oracle keeps one GraphQL file. The one item that the sibling module `crate::bootstrap` names, `QueryStringLimit`, is re-exported by `pub(crate) use query_string::QueryStringLimit;` in `graphql.rs`, because a `pub(crate)` item of a private module is not reachable from a sibling module (E0603).
3. the transport learns "opened" and "refused" through a `tokio::sync::watch` channel in per-request data, and the id of each result through an atomic in the same link. The resolver runs lazily inside the transport's poll of the response stream (Verified Library Facts 1), so a signal set by the resolver is the only reliable way to decide the status before the head. "Pending at the first poll" is not reliable, because `Subscription::next` yields cooperatively. The id must not come from the client's selection set, which may omit or alias `id` (FR-10).
4. a subscription takes its first step only after the transport called `release`, that is, after it decided to write the head. Without this gate, the first poll would run `Subscription::next` right after `open`, through `try_flatten`, and could start a Kafka page read or take a window page before the head. With it, the phase before the head registers a subscriber and reads nothing (FR-9, NFR-2), a subscription never produces a result before its head, and the three points of FR-9 are deterministic in tests.
5. the event object is parsed from the frame in the subscriber's task, and `Frame` gains no field. The publish path then does exactly what it does today (NFR-1). A frame from a replay is encoded per subscriber anyway (`subscription.rs:307-309`). Parsing into `async_graphql::Value` keeps the producer's member order whatever the features of `serde_json` are (Verified Library Facts 1), so `Event.data` equals the SSE `data` line member for member (FR-1).
6. `EventObject` derives `Eq` as well, because every field is `Eq` (`String`, and `Json<ConstValue>`) and `clippy::derive_partial_eq_without_eq` (nursery, enabled at warn and denied by `make.lint_code`) fires on a public type that derives only `PartialEq`; `EventTypeObject` and `EventStreamStatusObject` derive both for the same reason.
7. `data` carries `#[graphql(complexity = 501)]`, more than half of `MAX_COMPLEXITY` (1 000), so a document selects the event object at most once under any alias or fragment (FR-1, NFR-3, NFR-8), while `events(..) { id type data }` costs 504. The reason is a plain `//` comment, because a `///` line would join the GraphQL description of FR-1. The literal lives in the application crate, which cannot name the composition root's `MAX_COMPLEXITY`; the tests of both crates pin the relation (a second `data` refused, `{ id type data }` accepted).
8. `data` uses `Json<async_graphql::Value>` and not `serde_json::Value`. Both print as the scalar `JSON` with the description FR-1 names, but only the first keeps member order in a single-crate mutation run. Every field of `Event` is computed eagerly from the frame: the cost is one parse per event and subscriber, in the connection task, and the object needs no async resolver. Resolving `data` copies the value once more, and only once, because the document selects it at most once.
9. the GET rule differs from the POST rule because a GET of `/api/graphql` has no JSON representation: outside `dev` the event stream is its only representation, so a wildcard admits it (RFC 9110 12.5.1), while `text/html` keeps the explorer in `dev` and the 405 elsewhere. It removes at its root the 405 that Schemathesis's `Accept: */*` would get (Verified Library Facts 8), and every existing test, which sends no `Accept`, keeps its answer.
10. the GET parameters are decoded by a strict parser of the composition root and not by `axum::extract::Query`. `serde_urlencoded` decodes lossily: it keeps an invalid `%` sequence and replaces invalid UTF-8. FR-4 asks for a 400 in those cases. The 400 texts follow the wording of the existing query-string rejections.
11. on the GET form, `variables=null` and `extensions=null` are answered with the 422 violation, because FR-4 asks for a JSON-encoded object. The POST form keeps today's rule, where async-graphql reads `null` as empty (Verified Library Facts 1).
12. the rule is the direct-field rule of FR-14: one field selection written directly at the root, with no fragment at the root, the same response name twice counting as two. async-graphql 7.2.1 makes one stream per direct field selection and skips root fragments (Verified Library Facts 1). Under the looser wording of GraphQL specification 5.2.3.1, `{ events(..) { id } events(..) { type } }` would register two hub subscribers, and `{ ...F }` would run nothing. The direct-field rule keeps FR-14's goal, one request and one subscriber: it refuses more requests than the specification and never runs more or fewer than one subscriber. Fragments inside the selection set of `events` work as FR-10 says.
13. the rule is checked only on the event-stream transport, before `execute_stream`, and not as a schema extension. On the JSON transport a subscription that passes document validation keeps today's single error `Subscriptions are not supported on this transport.` whatever its root shape, and one that fails validation, such as `subscription { __typename }`, keeps async-graphql's validation error (FR-5), so NFR-17 holds for every request that does not negotiate SSE. The rule runs on the parsed document before async-graphql's validation, so a document that breaks both the rule and a validation rule is answered with the rule's error. FR-6 puts both in the same step.
14. the stream is written as bytes through `Body::from_stream`, because axum's `Event::data("")` cannot write the bare `data:` line of `complete` (Verified Library Facts 2). The head copies the three headers of the SSE route plus `vary`. It has no `charset`, no `connection` and no `content-encoding` (FR-7).
15. the transport reads the keep-alive from the `EventStreamState` that the bootstrap already puts into the schema data (Verified Library Facts 6), and not from a second settings value. The route state stays `State<ApiSchema>`, which the extractor oracle and every router test already use. One source of the interval means no duplicated setting, no bootstrap change for the POST form and no struct literal that a later story must extend. A schema built without the state, which only a test can build, answers the 500 problem. The GET form's bound is the one transport value that the state does not hold; it travels as `QueryStringLimit` (see `graphql/query_string.rs`).
16. the three GraphQL handlers that can answer an event stream take `HeaderMap`, the recorded streaming exception, and the two GET handlers also take `RawQuery`. Both extractors are infallible. `RawQuery` is the only way to apply the 414 bound to the query string "as received" and to parse it strictly. `ValidatedQuery` would reject a malformed query string before the handler could keep today's 405 for a GET that does not negotiate SSE. The extractor oracle names these two exceptions for the handlers `execute`, `subscribe` and `subscribe_or_explore` only, as the event-stream crate's oracle names its streaming handlers, and as NFR-13 states.
17. the router keeps today's split by environment. In `dev` it registers `get(subscribe_or_explore)`, otherwise `get(subscribe)`. No environment flag is added to the route state.
18. `Vary: accept` is set by a middleware outside the budget and the panic catcher, not by the handlers, so that FR-5's "every answer to a GET" holds literally, including the 503 and 500 that those two layers write after the handler is gone. A route-level layer sits inside the budget and could not reach them. POST answers pass unchanged, so the JSON transport gains no header.
19. three routers instead of one, because the GraphQL handlers take `State<ApiSchema>` (the extractor oracle and every router test rely on it) while the REST handlers take `AppState` and the operational ones nothing; utoipa merges their documents, and the axum routers merge after their states are applied. `AppState` gains no schema field.
20. the 403 problem of the origin check is documented on the WebSocket route only. The check answers any request that carries `Sec-WebSocket-Key` with an `Origin` outside the allow-list (`crates/service/src/http/origin.rs:41-59`), and only WebSocket handshakes carry that header; documenting it on every operation would describe a request no client of the other routes sends.
21. the event and frame schemas are new `ToSchema` types next to the handlers that answer them (`SseFrame` in the event-stream application crate's `http` module; `GraphQLRequest`, `GraphQLResponse` and `GraphQLEvent` in the composition root's `graphql` module), used only by the annotations; they are documentation types, not used to encode, so the wire bytes stay those of FR-8 and of bundle 4.
